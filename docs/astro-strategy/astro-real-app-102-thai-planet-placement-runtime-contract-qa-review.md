# ASTRO-REAL-APP-DEV-102 — Thai Planet Placement Runtime Contract QA Review

เอกสารทบทวนคุณภาพและข้อสัญญาการออกแบบตำแหน่งดาวเคราะห์ไทย (Runtime Contract QA Review) หลังจากการพัฒนาโมดูลจำลอง (DEV-099), ระบบกักกันความปลอดภัย (DEV-100), และตัวประสานรันไทม์ (DEV-101) เพื่อวางกรอบความมั่นคงทางข้อมูลและเตรียมพร้อมสำหรับขยายขอบเขตการทดสอบวินิจฉัยในขั้นถัดไป

---

## 1. Purpose (วัตถุประสงค์)

เอกสารฉบับนี้มีวัตถุประสงค์เพื่อประเมินและทบทวนความสมบูรณ์เชิงสถาปัตยกรรม (Architectural Integrity) ของสัญญารันไทม์ (Runtime Data Contract) ที่ถูกวางไว้ในโมดูลระบบตำแหน่งดวงดาวไทย โดยรับประกันว่าโครงสร้างชุดข้อมูล ความเสถียรเชิงระบบ และระดับการทดสอบความปลอดภัยจะทำงานสอดคล้องตามกรอบนโยบาย และสามารถกักกันข้อมูลจำลอง (Placeholder/Stub) ไม่ให้รั่วไหลไปสู่การเรนเดอร์ใน UI หรือเขียนทับข้อมูลประวัติสะสมของผู้ใช้

---

## 2. Scope & Non-Goals (ขอบเขตและสิ่งที่ไม่ใช่เป้าหมาย)

* **สิ่งที่ครอบคลุมการประเมิน (Scope)**:
  * การทบทวนโครงสร้างสถาปัตยกรรม 3 ชั้นรันไทม์ (Stub, Safety Harness, Orchestrator)
  * การตรวจสอบความปลอดภัยทางสัญญากับข้อมูลจำลองและเงื่อนไขเปรียบเทียบกรณีศึกษา
  * การวิเคราะห์และจำลองความเสี่ยงทางเทคนิค (Risk Matrix) ของระบบโค้ดตำแหน่งดวงดาว
  * การเสนอแนวทางการส่งต่อการพัฒนาเพื่อเข้าสู่เฟสการทดสอบเชิงลึก (DEV-103 Handoff Path)
* **สิ่งที่ไม่ใช่เป้าหมายในรอบนี้ (Non-Goals)**:
  * การแก้ไขหรือเขียนโค้ดโปรแกรมในส่วนรันไทม์เพิ่มเติมนอกเหนือจากเอกสารนี้
  * การดัดแปลงหรือแทรกแซงโครงสร้างการคำนวณลองจิจูด/ราศี/องศาของโหราศาสตร์ไทยจริง
  * การเปิดใช้งาน หรือเชื่อมฟังก์ชัน Adapter เข้าสู่ส่วนติดต่อผู้ใช้ (UI Wiring) หรือ LocalStorage

## 3. Runtime Stack Review (ทบทวนชั้นการทำงานรันไทม์)

ระบบประมวลผลตำแหน่งดาวเคราะห์ไทยถูกออกแบบในลักษณะแยกส่วน (Decoupled Design) และจัดวางสถาปัตยกรรมออกเป็น 3 ชั้น ดังนี้:

```mermaid
graph TD
    Input[ThaiPlanetPlacementInput] --> Orchestrator[DEV-101 Orchestrator Layer]
    Orchestrator --> Stub[DEV-099 Stub Layer]
    Orchestrator --> Safety[DEV-100 Safety Harness Layer]
    Stub --> |Generate 10 Planets| Results[ThaiPlanetPlacementResult[]]
    Safety --> |Verify Stub & Reference| Summary[ThaiPlanetPlacementSafetySummary]
    Orchestrator --> Output[ThaiPlanetPlacementRuntimeAdapterV01]
```

### 3.1 DEV-099 Stub Layer (ชั้นจำลองตำแหน่งดาวเคราะห์)
* **บทบาทหน้าที่**: ทำหน้าที่จำลองผลลัพธ์พิกัดดวงดาว ๐ ถึง ๙ โดยตอบสนองโครงสร้างโมเดลความจุประเภทข้อมูลตามเงื่อนไขทางวิศวกรรม
* **ผลประเมิน**: ข้อมูลพิกัดของดาวทุกดวงใน Stub จะถูกตรึงค่าตำแหน่งราศีและองศาเป็น `'pending-reference-validation'` และสถานะวิปริตเป็น `'unavailable'` เสมอ เพื่อความปลอดภัยทางสถิติและข้อมูล

### 3.2 DEV-100 Safety Layer (ชั้นกักกันความปลอดภัย)
* **บทบาทหน้าที่**: ทำหน้าที่ตรวจสอบสัญญาระหว่างข้อมูลผลลัพธ์รันไทม์กับตารางกรณีศึกษาควบคุม (Reference Case)
* **ผลประเมิน**: ระบบสามารถจำแนกค่า placeholder และ unavailable ออกจากกระบวนการตรวจสอบได้อย่างเด็ดขาด ส่งผลให้กระบวนการเปรียบเทียบกรณีศึกษาจำลองคืนค่าเป็นเทียบเคียงไม่ได้ (`not-comparable`) ตามเกณฑ์ความปลอดภัย

### 3.3 DEV-101 Orchestrator Layer (ชั้นประสานงานรันไทม์)
* **บทบาทหน้าที่**: ประสานโมดูล Stub และ Safety Harness ร่วมกันเพื่อสกัดและสับเปลี่ยนอินพุต/เอาต์พุตให้อยู่ในโมเดลเอกภาพ `ThaiPlanetPlacementRuntimeAdapterV01`
* **ผลประเมิน**: โมดูลประสานงานคืนค่า `adapterStatus` เป็น `'stub-only'` และ `inputStatus` เป็น `'pending'` ซึ่งเป็นไปตามแนวทางประกาศความระมัดระวัง (Not-validated metadata state)

## 4. Contract Checklist (เช็คลิสต์ตรวจสอบความสมบูรณ์ของสัญญา)

จากการตรวจสอบระบบความเชื่อมโยงของไฟล์ประเภทข้อมูลในระบบ โครงสร้างซอร์สโค้ดปัจจุบันผ่านเกณฑ์การประเมินสัญญารันไทม์อย่างครบถ้วนดังนี้:

* [x] **ดาวเคราะห์ ๐ ถึง ๙ ครบถ้วน (Planet IDs 0–9 Covered)**: รายการเอาต์พุตของผลลัพธ์มีจำนวนดาว 10 ดวง และถูกวนลูปจัดทำอย่างสอดคล้องตามรหัสประจำดาวเคราะห์
* [x] **การปฏิเสธค่าจำลอง (Placeholder remains non-validating)**: ค่าข้อความ `'pending-reference-validation'` ไม่ถูกประเมินเป็นสถานะถูกต้องหรือเทียบตรง (matched)
* [x] **การกักกันสถานะคลาดเคลื่อน (Unavailable remains non-validating)**: ค่าสถานะ `'unavailable'` ได้รับการปฏิบัติเสมือนค่าว่างและคัดกรองออกจากลอจิกความสอดคล้อง
* [x] **การสอบเทียบกรณีศึกษาจำลอง (Placeholder Reference remains not-comparable)**: เมื่อนำ Stub Results ไปทดสอบเปรียบเทียบกับ Reference Case ที่เป็นค่าจำลอง ผลสรุปทางสถิติต้องได้ `comparableCount: 0` และ `notComparableCount: 10`
* [x] **การประกาศสถานะอแดปเตอร์ (adapterStatus remains stub-only)**: มีการบังคับกำหนดสถานะตัวแปลงข้อมูลเป็น `'stub-only'` เสมอเพื่อระบุการกักขังลอจิก
* [x] **ข้อจำกัดของข้อมูลเวลา (generatedAt is metadata only)**: ฟิลด์ประทับเวลาถูกใช้เพื่อบันทึกประวัติการสร้างของรันไทม์เท่านั้น และไม่มีคำสั่งคำนวณพิกัดดาวดึงข้อมูลจากตัวแปรเวลานี้
* [x] **การแยกโครงสร้าง UI (No UI Integration)**: ยืนยันไม่มีการเรียกใช้ Import หรือแทรกแซงโค้ดใดๆ ภายใน `AstroTodayPanel.tsx` และ `AstroRealAppPreview.tsx`
* [x] **การแยกการจัดเก็บข้อมูล (No LocalStorage Interaction)**: ยืนยันไม่มีการเข้าถึงกลไกการเซฟหรือดึงข้อมูลผ่านการใช้ LocalStorage key ปลอมในชุดรหัสรันไทม์ใหม่
* [x] **ไม่มีตำแหน่งดาวและราศีสถิตจริง (No Real rasi/sign/degree values)**: ซอร์สโค้ดของไฟล์ตัวประสานและตัวแปลงปราศจากคำศัพท์หรือข้อมูลกลุ่มราศี/องศาดาราศาสตร์จริง

## 5. Risk Review (บทวิเคราะห์และระดับความเสี่ยงทางวิศวกรรม)

เพื่อความเสถียรภาพและความทนทานของแอปพลิเคชัน ขอชี้แจงประเด็นความเสี่ยงทางเทคนิคที่ควรเฝ้าระวังในการพัฒนาระยะยาว:

1. **ความเสี่ยงจากการเผลอประเมินค่าจำลองเป็นค่าถูกต้อง (Accidental Promotion of Placeholder)**:
   * *ลักษณะความเสี่ยง*: การอัปเดตฟังก์ชันเปรียบเทียบในอนาคต หากปล่อยปละละเลยความเข้มงวดของฟังก์ชัน `isPendingThaiPlanetPlacementValue` อาจทำให้รันไทม์ประเมินค่าจำลองกับกรณีศึกษาจำลองแล้วจับคู่ผ่านสำเร็จ (`matched`)
   * *แนวทางควบคุม*: จัดทำ Unit Test คุมเข้มพฤติกรรมการคืนค่า false ของความเข้ากันได้ (Comparable constraints) เสมอ
2. **ความเสี่ยงจากการแสดงผลตำแหน่งดาวจำลองบนหน้าจอผู้ใช้จริง (Future UI Displaying Stub as Real)**:
   * *ลักษณะความเสี่ยง*: การเชื่อมโยง UI ในอนาคตหากไม่มีการเช็คสถานะ `adapterStatus` หรือ `validationStatus` อาจนำเอาค่าจำลอง `'pending-reference-validation'` ไปแสดงผลบนหน้าจอแผงข้อมูลจนผู้ใช้เข้าใจผิด
   * *แนวทางควบคุม*: การเรนเดอร์ใน UI ต้องมีเงื่อนไขเปิดเผยข้อความเตือนหรือบล็อกไม่แสดงค่าข้อมูลหากพบสถานะ `'stub-only'` หรือมีค่าเป็น pending
3. **ความเสี่ยงจากการนำเวลาประทับไปอ้างอิงเป็นฐานคำนวณตำแหน่งดาว (generatedAt Misuse)**:
   * *ลักษณะความเสี่ยง*: หากนักพัฒนานำฟิลด์ `generatedAt` ไปเป็นข้อมูลนำเข้าในการประมาณความเร็วการเคลื่อนตัวของดวงดาว จะทำให้ระบบได้ตำแหน่งดาวที่ขยับเขยื้อนตามเวลาโหลดหน้าเว็บ (Non-deterministic outputs)
   * *แนวทางควบคุม*: ควบคุมให้ข้อมูลตำแหน่งดาวคำนวณจากอินพุตเวลาเกิด (`birthTime`) และวันเกิด (`birthDate`) ของผู้ใช้ที่ผ่านการกรอกแบบฟอร์มอย่างเป็นทางการเท่านั้น
4. **ความเสี่ยงของสัญญาคุณสมบัติไทป์ข้อมูลที่กว้างเกินไป (Permissive Type Contract)**:
   * *ลักษณะความเสี่ยง*: การเปลี่ยนแปลงไทป์ข้อมูลเอาต์พุตให้เป็นประเภท `any` หรือ `unknown` จะทำให้ TypeScript compiler ตรวจไม่พบข้อบกพร่องสะสมระหว่างชั้นประมวลผล
   * *แนวทางควบคุม*: กำหนดให้ Adapter ทำงานภายใต้การประกาศ Typecasting และคลาสอินเทอร์เฟซที่ระบุเข้มข้นใน `astroRealAppTypes.ts` เสมอ
5. **ความเสี่ยงจากกรณีเปรียบเทียบคาดเคลื่อนในอนาคต (Future Reference Case Mismatch)**:
   * *ลักษณะความเสี่ยง*: เมื่อขึ้นปฏิทินจริงและการสอบเทียบในเฟสถัดไป ข้อมูลดวงชะตากรณีศึกษาที่คัดลอกมาอาจคลาดเคลื่อนไปจากระบบที่ใช้งานจริง
   * *แนวทางควบคุม*: รักษาความสะอาดและใช้กรณีศึกษาจากระบบอ้างอิงโหราศาสตร์ไทยที่ตกลงกันไว้ (เช่น MyHora คอนโทรลเคส)

## 6. DEV-103 Handoff Recommendation (ข้อเสนอแนะการส่งมอบงานถัดไป)

เพื่อขยายผลลัพธ์การพัฒนาในขอบเขตความปลอดภัยเชิงระบบ และป้องกันผลกระทบข้างเคียงเชิงลึกก่อนการเชื่อม UI ขอแนะนำแนวทางสำหรับดำเนินงานใบงาน **DEV-103** ออกเป็น 2 ทางเลือก:

### ทางเลือกที่ A (แนะนำ): `DEV-103 — Thai Planet Placement Diagnostic Unit Test / Manual Fixture Review`
* **รายละเอียด**: จัดทำไฟล์สำหรับจำลองเคสชุดข้อมูลทดสอบ (Diagnostic Test Fixtures) โดยทำการเขียนสคริปต์รัน Unit Test แยกเพื่อยืนยันพฤติกรรมความปลอดภัยของฟังก์ชันกักกันข้อมูล (Safety Harness) และตัวประสานงาน (Orchestrator) ภายใต้กรณีป้อนค่าจำลองต่างๆ โดยตรง
* **ข้อดี**: การันตีความปลอดภัยและ contract verification ผ่านชุดตรวจสอบอย่างเปรียบเทียบได้อย่างเป็นรูปธรรม ก่อนการเริ่มเขียนโค้ดผูกกับ UI

### ทางเลือกที่ B: `DEV-103 — Thai Planet Placement Runtime Integration Plan`
* **รายละเอียด**: จัดทำเอกสารวางแผนและประเมินผลกระทบเชิงบูรณาการโครงสร้างข้อมูลลอจิก สำหรับนำตัวประสานงาน (Orchestrator) ไปประกอบเข้ากับโมดูลคํานวณกลางของระบบ
* **ข้อดี**: เตรียมกรอบการทำงานสำหรับการผสานชั้นข้อมูล (Astro Engine) ได้รวดเร็ว

*ข้อสังเกตความปลอดภัย: ทั้งสองทางเลือกข้างต้นยังคงยึดนโยบายเอกเทศและไม่มีการเชื่อมต่อหรือแก้ไขไฟล์แสดงผลหลัก (UI wiring) ในหน้าจอเพื่อความเสถียรสูงสุด*
