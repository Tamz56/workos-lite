# Thai Planet Diagnostic Runtime Assertion Runner Plan (ASTRO-REAL-APP-DEV-117A)

เอกสารวางแผนจัดสร้างสเปกสำหรับอัปเกรดตัววินิจฉัยและสคริปต์ตรวจวัดสัญญาความสอดคล้องเชิงรันไทม์ (Runtime Assertion Runner Plan) ของปฏิทินดาวไทยจำลอง v0.1

---

## 1. Purpose (วัตถุประสงค์)

วัตถุประสงค์ของการจัดทำแผนนี้คือการออกแบบระบบตรวจสอบสัญญาการแลกเปลี่ยนข้อมูลเชิงรันไทม์อัตโนมัติ (Runtime Assertion Runner) ในอนาคต โดยอัปเกรดจากสคริปต์ตรวจความสอดคล้องด้วยมือในปัจจุบัน เพื่อให้สามารถทดสอบความถูกต้องเชิงโครงร่างประเภทข้อมูล ความมั่นคงเชิงอินเทอร์เฟส และความปลอดภัยจากการไหลของข้อมูลจำลองอย่างแม่นยำและเข้มงวด โดยยังคงควบคุมไม่ให้มีการเขียนลอจิกการประมวลผลดวงดาวจริง หรือคำบรรยายทำนายจริงเกิดขึ้นในโครงการหลัก

---

## 2. Scope & Non-goals (ขอบเขตและข้อยกเว้น)

### ขอบเขตในการวางแผน (In Scope)
* การจัดทำแผนเชิงสเปก (Planning and specs only)
* การนิยามกลุ่ม Assertion การทดสอบในอนาคต (Assertion Categories)
* การกำหนดเงื่อนไขพิจารณาความล้มเหลว (Failure Policy) และตัวตรวจสอบคำพูดเฝ้าระวัง (Copy Safety Guard)
* การนำเสนอสถาปัตยกรรมทางเลือกของระบบรันเนอร์

### ข้อยกเว้นการทำงาน (Non-goals)
* ไม่ใช่การลงมือเขียนโค้ดสคริปต์หรือโปรแกรมตัวตรวจสอบรันเนอร์ในรอบนี้
* ไม่มีการสร้างหรือแก้ไขไฟล์โค้ดใน `src/` หรือ `scripts/`
* ไม่ดึงพิกัดดาราศาสตร์จริง หรือคำนวณตำแหน่งองศาดาวเคราะห์จริง
* ไม่เข้าเชื่อมต่อกับ LocalStorage หรือประมวลผลคำทำนายลงบน UI แต่อย่างใด

## 3. Current Manual Script Review (การประเมินสคริปต์ในปัจจุบัน)

สคริปต์ตรวจวัดสัญญาดวงดาวด้วยมือในปัจจุบันคือ `scripts/astro-diagnostics/check-thai-planet-placement-contract.cjs` ซึ่งทำงานผ่านสภาพแวดล้อม Node.js โดยคืนค่าผลลัพธ์ผ่าน terminal เป็น `Status: Passed` เมื่อสอดคล้องตามกฎเกณฑ์:

* **Planet ID coverage**: ตรวจเช็กว่ามีรายชื่อดาวเคราะห์จำลองครบถ้วนทั้ง 10 ดวง (1-9 และ 0)
* **Placeholder non-validation**: ตรวจสอบว่าค่าขององศาและราศีไม่มีการอ้างอิงตำแหน่งจริง
* **Comparable count guard**: ตรวจจับว่าจำนวนเปรียบเทียบในกรณีทดสอบต้องเป็น 0 เสมอ
* **Not-comparable guard**: ยืนยันว่าการตั้งค่าไม่เปรียบเทียบต้องครบ 10 จุด
* **Adapter status guard**: ยืนยันสถานะการทำงานของอะแดปเตอร์เป็น `"diagnostic"`
* **Metadata-only generatedAt**: ตรวจวัดว่าตัวแปรเวลาเป็นเพียง metadata
* **UI isolation**: เช็กว่าคอมโพเนนต์ย่อยของดวงดาวไทยไม่ได้อิมพอร์ตเข้าไปที่ระบบหลักโดยพลการ
* **LocalStorage isolation**: ตรวจสอบการไม่มีคำสั่งเขียน Storage ภายในอะแดปเตอร์จำลอง

## 4. Proposed Future Runner Goal (เป้าหมายของรันเนอร์ในอนาคต)

เป้าหมายสูงสุดคือการสร้างตัวตรวจสอบที่สามารถดักจับการดัดแปลงสัญญาและเช็กความสอดคล้องของตัวประสาน (Interface contracts) ได้โดยตรงที่ระดับการคอมไพล์และทดสอบอัตโนมัติ (CI Pipeline) โดยเน้น **"การตรวจสอบสัญญารันไทม์ของข้อมูลจำลอง" (Technical Contracts)** ไม่ใช่การตัดสินคุณภาพความแม่นยำทางโหราศาสตร์ดาราศาสตร์ (Not for astrology accuracy) และ **ห้ามให้ระบบรันเนอร์นี้กลายเป็นตัวเทียบดวงจริง (Not an oracle for real charts)** ในทุกกรณี

---

## 5. Proposed Assertion Categories (หมวดหมู่ข้อตกลงและตรวจสอบที่วางแผน)

อนาคตของระบบตรวจสอบ Assertion จะถูกแบ่งออกเป็นประเภทต่างๆ:

* **Planet ID Coverage Assertion**: บังคับให้ระบบรันไทม์จำลองต้องจัดส่งพิกัดดาวเคราะห์ครอบคลุม id 0 ถึง 9 เท่านั้น ห้ามขาดหรือเกิน
* **Placeholder-Only Value Assertion**: ตรวจจับเชิงรันไทม์ว่าค่าองศา ลิปดา ราศี หรือคำบรรยาย ต้องสอดคล้องตามฟิกซ์เจอร์จำลองและไม่มีค่าข้อมูลจริงหลุดรอด
* **Adapter Status Assertion**: ตรวจสอบค่าฟิลด์สถานะของอะแดปเตอร์ให้คืนค่า `"diagnostic"` และตัวแปรเวอร์ชันจำลอง `"stub-v0.1"` เสมอ
* **Safety Summary Assertion**: ยืนยันว่าข้อมูลความปลอดภัยสัญญารุ่นทดลองถูกแนบอยู่ในรันไทม์
* **Comparison Status Assertion**: บังคับให้ flag ในการเทียบความเที่ยงตรง คืนค่าไม่สามารถเปรียบเทียบได้ในกรณีทดลองทั่วไป
* **Not-Comparable Guard Assertion**: ตรวจสอบว่าระบบส่งค่าข้อยกเว้นการประมวลผลดวงดาวครบถ้วนทั้ง 10 มิติ
* **generatedAt Metadata Assertion**: ตรวจสอบว่า `generatedAt` คืนค่ารูปแบบ ISO สตริงที่ถูกต้องโดยไม่นำมาผ่านกระบวนการแปลงค่าปฏิทิน
* **No Persistence Assertion**: สแกนโค้ดและรันไทม์เพื่อให้มั่นใจว่าไม่มี Side-effect กับ Storage
* **No Strategy Contamination Assertion**: ตรวจเช็กพฤติกรรมการแลกเปลี่ยนข้อมูลว่าไม่มีการส่งต่อ `runtimeResult` ไปหาคอมโพเนนต์การวิเคราะห์กลยุทธ์หลัก
* **Copy Safety Label Assertion**: สแกนตรวจสอบป้ายคำเตือนการวินิจฉัยว่ายังคงเรนเดอร์ครบถ้วนตามหลักเกณฑ์ความปลอดภัยของคำอธิบายภาษา

## 6. Proposed Fixture Strategy (นโยบายชุดข้อมูลทดสอบ)

* **Placeholder-only**: ระบบจะใช้ฟิกซ์เจอร์จำลองความปลอดภัย (In-memory Placeholder Fixtures) เท่านั้น โดยป้อนค่าวันเกิดและเวลาเกิดเป็น `"pending-reference-validation"` และพิกัดสถานที่เกิดระบุสถานะเดียวกัน
* **No Real Profile**: จะไม่มีการดึงข้อมูลโปรไฟล์วันเกิดจริงของผู้ใช้จาก LocalStorage หรือเขียน Mock Data ที่เป็นตำแหน่งราศีและองศาของดวงดาวจริงมาป้อนเข้าสู่การทดสอบเด็ดขาด

## 7. Proposed Runner Architecture Options (ตัวเลือกโครงสร้างสถาปัตยกรรมรันเนอร์)

### Option A — คงรูปแบบสคริปต์ CommonJS (CJS) แต่เสริมสเปกการตรวจสอบ Assertion
* **แนวทาง**: เขียนชุดคำสั่งเช็กที่เข้มข้นขึ้นในสคริปต์ `check-thai-planet-placement-contract.cjs` เดิม โดยไม่อ้างอิงประเภทข้อมูลของ TypeScript บนรันไทม์
* **การประเมิน**: ความเสี่ยงต่ำสุด แต่ขาดการเชื่อมโยงกับ Type definitions

### Option B — ใช้ TypeScript Runner ผ่านโปรแกรม tsx ที่ติดตั้งอยู่ในเครื่อง
* **แนวทาง**: พัฒนาตัวรันเนอร์เป็นไฟล์ `.ts` และรันผ่านคำสั่ง `npx tsx` เพื่อให้ตรวจสอบสัญญาร่วมกับ TypeScript interface ได้ทันที
* **การประเมิน**: มีประโยชน์สูงในการตรวจสอบความถูกต้องของสัญญากับประเภทข้อมูล แต่ต้องเช็กว่าในเครื่องปัจจุบันมีโปรแกรม `tsx` ติดตั้งอยู่แล้วในโลคอลโดยไม่เพิ่ม dependencies

### Option C — ติดตั้ง Package Script ใน package.json
* **แนวทาง**: เพิ่มคำสั่งสคริปต์สำหรับรันตัวตรวจสอบใน `package.json` (เช่น `"test:astro-diagnostics"`)
* **การประเมิน**: ทำได้สะดวกสำหรับทีมพัฒนา แต่จะยังไม่ดำเนินการจนกว่าแผนภาพรวมจะผ่านการประเมินสัญญารันไทม์

### Option D — คงความสะอาดของ package.json และเรียกใช้ด้วยคำสั่ง Node.js ตรงผ่าน CJS/ESM
* **แนวทาง**: รันตัวสคริปต์จำกัดวงผ่านคำสั่ง `node` บนเทอร์มินัลโดยระบุไฟล์ตรง และไม่แก้ไขค่ากำหนดของโปรเจกต์หลัก
* **การประเมิน**: ปลอดภัยสูง ป้องกันการปะปนรหัสทดสอบเข้าไปในกระบวนการบิวด์ของโปรดักชัน

> [!TIP]
> **ข้อแนะนำสถาปัตยกรรม (Recommended Option)**: บูรณาการคำแนะนำร่วมระหว่าง **Option B (ร่วมกับ CJS/ESM)** และ **Option D** โดยการสร้างไฟล์ตรวจสอบอิสระแยกจากระบบบิวด์ และหลีกเลี่ยงการแก้ไข `package.json` เพื่อกักบริเวณโค้ดการทำ QA

## 8. Dependency Policy (นโยบายการใช้ Dependencies)

* **No New Dependency**: ห้ามดาวน์โหลดหรือเพิ่มแพ็คเกจเพิ่มเติมใน `package.json` เด็ดขาด
* **Local tsx Check**: หากตรวจสอบพบว่าโครงการมี `tsx` ติดตั้งอยู่ในเครื่องภายใน `.bin` อยู่แล้ว สามารถพิจารณาเรียกใช้งานแบบจำกัดขอบเขตได้ตามความเหมาะสม แต่การรันโดยเครื่องมือมาตรฐานของ Node.js Core API ในระบบ CommonJS/ESM จะเป็นแนวทางที่ปลอดภัยสูงสุดและได้รับความสำคัญเป็นลำดับแรก

ตัวตรวจสอบผลลัพธ์ในอนาคตควรนำเสนอโครงสร้างรายงานที่กระชับและเข้าใจง่าย:


## 10. Failure Policy & Non-zero Exit (เงื่อนไขความล้มเหลวเชิงทดสอบ)

เพื่อป้องกันการข้ามผ่านข้อบกพร่องโดยไม่ได้ตั้งใจ (Silent Passes):
* ตัวระบบรันเนอร์ในอนาคตต้องส่งกลับรหัสผลลัพธ์สิ้นสุดการทำงานเป็นค่าอื่นที่ไม่ใช่ศูนย์ (`process.exit(1)`) เมื่อพบความล้มเหลวของ Assertion แม้เพียงจุดเดียว
* **เงื่อนไขสำคัญที่ต้องปฏิเสธ (Must Fail if):**
  * จำนวนดาวเคราะห์จำลองไม่ได้สัดส่วน (ไม่เท่ากับ 10 ดวง)
  * สถานะของ อะแดปเตอร์ หรือความปลอดภัยถูกดัดแปลงเป็นสถานะอื่นที่ไม่ใช่สัญญารุ่นทดลองวินิจฉัย
  * มีการตรวจพบข้อมูลราศีจริงหรือองศาจริงที่ดูเหมือนเป็นผลดวงจริง (Real Rasi/Degrees)
  * มีประวัติการเรียกเขียนค่าหรือเก็บ cache ข้อมูลทดลองลงใน LocalStorage
  * มีการประมวลผลคำเตือนภาษาที่ไม่ครบถ้วนหรือมีคำต้องห้ามปะปน

---

## 11. Copy Safety Guard (การตรวจสอบภาษาความปลอดภัยคำทำนาย)

* ระบบทดสอบหรือกระบวนการตรวจสอบเอกสาร QA จะทำการสแกนคำและเฝ้าระวังเพื่อแจ้งความเสี่ยงเมื่อตรวจพบคำที่มีความหมายเชิงยืนยันความถูกต้องของดวงจริงในไฟล์รหัสหรือการออกคำทำนาย เช่น:
  `accurate placement`, `real chart`, `ดาวอยู่ราศี…`, `ผลดวงจริง`, `ใช้ทำนาย`, `validated placement`
* เมื่อตรวจพบระบบต้องแจ้งเตือนพร้อมหยุดกระบวนการคอมไพล์ทันที

---

## 12. LocalStorage & Strategy Guard (ระบบคัดกรอง Storage และการปะปนข้อมูล)

* ตัวตรวจสอบรันเนอร์จะไม่เรียกใช้คำสั่งเพื่อรันบนเบราว์เซอร์จริง แต่จะอาศัยวิธีการทำ **Static Code Analysis** และทดสอบหน่วยย่อย (Unit Testing simulation) เพื่อยืนยันว่าไม่มีคำสั่งอย่าง `localStorage.setItem` หรือการส่งมอบข้อมูล `runtimeResult` เข้าสู่คอมโพเนนต์วิเคราะห์กลยุทธ์หลัก `AstroTodayPanel` หรือ `Composer`

## 13. Risk Review (บทวิเคราะห์ความเสี่ยงเชิงทดสอบ)

| ปัจจัยเสี่ยงเชิงระบบ | ระดับผลกระทบ | แนวทางกักกันความเสี่ยงที่วางแผนไว้ |
|---|---|---|
| รันเนอร์กลายสภาพเป็นเครื่องมืออ้างอิงดวงจริง (Oracle Risk) | สูง | ล็อกสัญญารับข้อมูลด้วยค่า placeholder-only ตลอดไป ห้ามคำนวณตำแหน่งจริง |
| การเข้าใจผิดว่าเทสผ่านแปลว่าการคำนวณดวงจริงเที่ยงตรง | ปานกลาง | ป้ายกำกับบนหัวรายงานต้องพิมพ์ตัวพิมพ์ใหญ่ระบุเป็นเครื่องวินิจฉัยจำลอง |
| การเพิ่ม dependencies ในอนาคตทำให้โค้ดหลักบวม | ต่ำ | ยึดนโยบายใช้เฉพาะ Node.js Core API และเครื่องมือเดิมในเครื่องเท่านั้น |
| การนำระบบไปเชื่อมต่อกับ Production Build | ต่ำ | ใช้ static checks และจำกัดสคริปต์ไว้ในหมวดพัฒนาวินิจฉัยย่อย |
