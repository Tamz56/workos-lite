# ASTRO-REAL-APP-DEV-104 — Thai Planet Placement Manual Diagnostic Script Plan

เอกสารแผนจัดทำและแนวทางการรันสคริปต์วินิจฉัยพฤติกรรมข้อมูลด้วยมือ (Manual Diagnostic Script Plan) สำหรับตรวจสอบความถูกต้องของสัญญารันไทม์ตำแหน่งดวงดาวไทย v0.1 เพื่อยืนยันว่าการกักภัยค่าจำลองและตัวประสานงานจะทำงานเป็นเอกเทศและไม่ส่งผลข้างเคียงต่อระบบจริง

---

## 1. Purpose (วัตถุประสงค์)

ใบงาน **DEV-104** มีวัตถุประสงค์เพื่อกำหนดแผนงานและข้อกำหนดการทำงานของสคริปต์ตรวจสอบสัญญาพฤติกรรมรันไทม์ด้วยมือ (Manual Diagnostic Script) เพื่อใช้รันประเมินความปลอดภัยเชิงโครงสร้างรันไทม์ของระบบดวงดาวไทยปฏิทินไทย v0.1 โดยช่วยยืนยันและควบคุมสัญญารันไทม์ให้อยู่ในสถานะกักภัย ป้องกันไม่ให้โค้ดการทำงานในส่วนของ Adapter รั่วไหลและขยายขอบเขตอย่างคลาดเคลื่อน

---

## 2. Scope & Non-Goals (ขอบเขตและสิ่งที่ไม่ใช่เป้าหมาย)

* **สิ่งที่ครอบคลุม (Scope)**:
  * การกำหนดแนวทางและตำแหน่งจัดวางไฟล์สคริปต์ทดสอบวินิจฉัยควบคุมในอนาคต
  * การกำหนดบทบาท ความรับผิดชอบ และคุณลักษณะของชุดสคริปต์ทดสอบ
  * การออกแบบตารางกรณีศึกษาทดสอบ (Diagnostic Fixture Plan) ในสเปกเอกสาร
  * การกำหนดรูปแบบการพิมพ์ข้อมูลการรายงานผลผ่านเทอร์มินัล (Terminal Output Format)
  * การกำหนดเกณฑ์ความเสี่ยงและการเสนอแนะการส่งมอบงานถัดไป (DEV-105 Handoff)
* **สิ่งที่ไม่ใช่เป้าหมายในรอบนี้ (Non-Goals)**:
  * การสร้างไฟล์เขียนโค้ดเขียนโปรแกรมที่สั่งการรันได้จริงในรอบนี้ (No executable scripts created)
  * การดัดแปลงหรือแก้ไขโค้ดการคำนวณภายในไดเรกทอรี `src/` ทั้งปวง
  * การแก้ไข ดัดแปลง หรือเชื่อมโยงเข้าสู่กลไกหน้าจอ UI หรือข้อมูล LocalStorage

## 3. Proposed Future Script Location (แนวทางตำแหน่งจัดวางสคริปต์ในอนาคต)

ในการพัฒนาขั้นตอนทดสอบระยะถัดไป (เช่น ใน DEV-105) มีการเสนอให้จัดวางไฟล์สคริปต์สำหรับรันด้วยมือไว้ที่:
`scratch/astro-diagnostics/check-thai-planet-placement-contract.cjs`

*ข้อกำหนดการควบคุมความปลอดภัยของไฟล์ในอนาคต*:
* **ความเป็นเอกเทศภายในเครื่อง (Local-only)**: สคริปต์นี้ต้องถูกจัดหมวดหมู่ให้ทำงานแบบรันด้วยมือผ่าน CLI เท่านั้น และจะไม่ถูกจัดทำหรือบันทึกเพื่อรันในโปรดักชัน
* **การป้องกันไม่ให้ถูกคอมไพล์ใน UI**: จะต้องไม่มีการนำเข้า (Import) หรือดึงฟังก์ชันจากไฟล์สคริปต์นี้เข้าสู่ระบบโครงสร้างหลักและหน้าเว็บแสดงผลโดยเด็ดขาด
* **การกันออกจากสารบบ Git**: ไฟล์ในตำแหน่ง `scratch/*` ได้รับการจัดกฎละเว้นผ่านความปลอดภัยใน `.gitignore` เรียบร้อยแล้ว (ตามข้อ MAINT-001) ทำให้ไฟล์ทดสอบชั่วคราวนี้จะไม่ถูกบันทึกหรือติดตามเข้าสู่ประวัติ Git ของโปรเจกต์ในอนาคต

## 4. Diagnostic Script Responsibilities (ความรับผิดชอบของสคริปต์วินิจฉัย)

ชุดสคริปต์ทดสอบในอนาคตจะมีหน้าที่และขอบเขตการตรวจสอบที่จำกัดอย่างเข้มงวด ดังนี้:
1. **การนำเข้าที่ปลอดภัย (Controlled Import)**: ทำการอิมพอร์ตหรือดึงฟังก์ชัน Adapter และ Safety Harness จากไฟล์ `src/components/workspaces/astro-strategy/real-app/data/` ภายใต้โมดูล CommonJS/ESM
2. **การป้อนข้อมูลจำลอง (Placeholder Input Setup)**: ดำเนินการจำลองข้อมูลอินพุตประเภทจำลอง (Placeholder values) ป้อนให้แก่ Orchestrator
3. **การตรวจสอบผลลัพธ์ตำแหน่งดาว (Orchestration Check)**:
   * ยืนยันผลลัพธ์ว่าต้องได้ดวงดาวครอบคลุม Planet IDs 0 ถึง 9 ครบทั้ง 10 ดวง
   * ตรวจสอบว่าพิกัดราศีสถิต (`signRasi`) และองศา (`degree`) ทุกดวงคงค่า `'pending-reference-validation'` หรือ `'unavailable'` เท่านั้น
4. **การประเมินสัญญาความมั่นคง (Safety Summary Match Guard)**:
   * ยืนยันว่าค่าตัวนับสถิติ `comparableCount` ต้องเป็น 0 เสมอเมื่อตรวจสอบเทียบเคียงกรณีศึกษาจำลอง
   * ยืนยันว่าค่า `notComparableCount` ได้สถิติเท่ากับ 10 เสมอสำหรับกรณี placeholder reference case
   * ยืนยันว่าคุณลักษณะ `adapterStatus` ได้ผลลัพธ์ตรงกับคำว่า `'stub-only'`
5. **การพิมพ์รายงานสรุปผล (Console Reporting)**: พิมพ์ข้อความรายงานผลตรวจสอบความสอดคล้อง (Passed / Failed) ของการเช็คสัญญาข้อมูลอย่างรวดเร็วผ่าน Console CLI

## 5. Fixture Plan (ตารางกรณีวินิจฉัยจำลอง)

แผนการจัดทำชุดอินพุตและค่าคาดหวังในเอกสารการวางแผนนี้ กำหนดโครงสร้างข้อมูลจำลองควบคุม 100% ปราศจากการใช้คำศัพท์และตำแหน่งดาวเคราะห์โหราศาสตร์ไทยจริง:

* **TH-PLANET-DIAG-001: Stub-only placeholder input**
  * *อินพุต*: ปฏิทินและกลไกคำนวณเป็น `'pending-reference-validation'`
  * *เกณฑ์สอบผ่าน*: ผลลัพธ์จำนวนดาวเท่ากับ 10 และเอาต์พุตตำแหน่งรายดวงทุกดวงเป็น `'pending-reference-validation'`
* **TH-PLANET-DIAG-002: Placeholder reference case comparison**
  * *อินพุต*: สอดแทรกกรณีศึกษาคาดหวังที่มีคุณสมบัติเป็น `'pending-reference-validation'` ทั้งหมด
  * *เกณฑ์สอบผ่าน*: สถิติได้ `comparableCount` = 0 และ `notComparableCount` = 10
* **TH-PLANET-DIAG-003: Unavailable value guard**
  * *อินพุต*: ข้อมูลผลลัพธ์มีค่าจำลองสถิตเป็น `'unavailable'`
  * *เกณฑ์สอบผ่าน*: ตัววิเคราะห์ตรวจจับและประเมินเป็น non-validating และไม่ส่งผลเป็น matched
* **TH-PLANET-DIAG-004: No referenceCase diagnostic mode**
  * *อินพุต*: พารามิเตอร์ของกรณีศึกษาอ้างอิงเป็น `undefined`
  * *เกณฑ์สอบผ่าน*: ระบบให้ผลประเมินสรุปเป็นหมวดวินิจฉัยชั่วคราว (Diagnostic only)
* **TH-PLANET-DIAG-005: System mismatch placeholder note**
  * *อินพุต*: ระบบกลไกการคำนวณของรันไทม์คลาดเคลื่อนไม่ตรงกับกรณีศึกษา
  * *เกณฑ์สอบผ่าน*: ตัวประเมินความเข้ากันได้ปฏิเสธสิทธิการตรวจและบันทึกรายงาน mismatch ลงใน issues

## 6. Expected Output Format (รูปแบบการรายงานผลลัพธ์)

เมื่อสั่งการรันสคริปต์ประเมินความปลอดภัยในอนาคต ข้อมูลรายงานผลที่พิมพ์ออกคอนโซลควรรักษามาตรฐานรูปแบบที่กระชับและตรวจสอบได้ง่ายดังนี้:

```text
Status: Passed / Partial / Failed
Checks:
- Planet ID coverage: Passed
- Placeholder non-validation: Passed
- Comparable count guard: Passed
- Not-comparable guard: Passed
- UI isolation: Passed
- LocalStorage isolation: Passed
```

## 7. Safety Rules for Future Scripts (กฎความปลอดภัยในการพัฒนาสคริปต์)

เพื่อควบคุมพฤติกรรมระบบให้ปราศจากความเสี่ยงทางข้อมูลอันไม่พึงประสงค์ สคริปต์ทดสอบที่เขียนในอนาคตต้องไม่ละเมิดกฎเหล็กดังต่อไปนี้:
* **ห้ามตัดสินตำแหน่งดาวจริง**: ห้ามมีชุดคำสั่งยืนยันหรือตรวจสอบพิกัดองศาหรือราศีจริงตามหลักการพยากรณ์
* **ห้ามเคลมความถูกต้องของค่าจำลอง**: ห้ามมองว่าการได้ค่า placeholder มาเปรียบเทียบเป็นการจับคู่สำเร็จลุล่วงแบบ matched
* **ห้ามบันทึกหรือทำลายไฟล์**: สคริปต์ต้องทำงานในลักษณะ Read-only ป้อนจำลอง In-memory และห้ามเขียน แก้ไข หรือลบไฟล์ซอร์สโค้ดในไดเรกทอรีหลัก
* **ห้ามแก้ไขข้อมูลแอป**: ห้ามสอดแทรกคำสั่งที่เปลี่ยนแปลงข้อมูลการบันทึกสถานะหรือบันทึกประวัติการใช้ของผู้ใช้

## 8. Risk Review (บทประเมินความเสี่ยงทางเทคนิค)

1. **ความเสี่ยงสคริปต์เป็นเท็จและส่งสัญญาณผ่านปลอม (Diagnostic script becoming a false oracle)**:
   * *คำอธิบาย*: สคริปต์อาจถูกเขียนให้ประเมินผ่านเสมอโดยไม่มีการส่งพารามิเตอร์วิเคราะห์จริง ทำให้ไม่พบข้อบกพร่องสะสม
   * *แนวทางควบคุม*: ต้องมีการเขียน Assertion แบบเข้มงวดระบุให้ชัดเจนถึงจำนวนตัวแปรที่จับคู่ได้ตามจริง
2. **ความเสี่ยงจากการนำข้อมูลทดสอบไปอ้างอิงเป็นดวงจริง (Fixture data mistaken for real astrology)**:
   * *คำอธิบาย*: นักพัฒนาในอนาคตอาจนำเอา Fixtures ในสคริปต์ไปอนุมานว่าเป็นกรณีศึกษาที่ผ่านการพิสูจน์องศาแล้ว
   * *แนวทางควบคุม*: ประทับป้ายกำกับ `'Diagnostic Placeholder'` ที่หัวของชุดข้อมูลในโค้ดเสมอ
3. **ความเสี่ยงสคริปต์หลุดเข้าไปเป็นส่วนหนึ่งของระบบ UI (Accidentally becoming a production dependency)**:
   * *คำอธิบาย*: การเผลอนำเข้าชุดสคริปต์หรือฟังก์ชันจากโฟลเดอร์ทดสอบเข้าสู่ระบบรันไทม์จะทำให้ขนาดแอปใหญ่ขึ้นโดยไม่จำเป็น
   * *แนวทางควบคุม*: การอิมพอร์ตข้อมูลต้องกระทำทางฝั่ง Node.js CLI และแยกส่วนออกจากกระบวนการบิวด์ของ webpack (Next.js)

* **ข้อจำกัดสคริปต์ใน DEV-105**:

  - ทำหน้าที่เพียงรวบรวมฟังก์ชันและรายงานผลประเมินความปลอดภัยเชิงโครงสร้างรันไทม์จำลอง (Stub, Safety Summary) โดยไม่มีการแก้ไข LocalStorage หรือทำงานร่วมกับ UI ใดๆ
