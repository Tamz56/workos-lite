## 2. Navigation Decision (การตัดสินใจตำแหน่งเมนู)

การเลือกใช้นโยบาย **Option C — Hybrid** มีรายละเอียดและข้อตกลงในการออกแบบความสัมพันธ์ดังนี้:

### รูปแบบปฏิสัมพันธ์ (Interaction Pattern - Locked for V1)
* **พฤติกรรมการเชื่อมโยงหลัก**: 
  `Daily Timing Summary Card (บน Daily Brief) → เปิดหน้าจอเต็มสำหรับการวิเคราะห์ (Strategic Timing Full View)`
* **การเปิดใช้งาน**: แสดงผล Summary Card ท้ายหน้า Daily Timing Brief (แสดงธีมจังหวะหลักของวันนี้, supportive window และ caution window ย่อยสั้น ๆ) โดยมีปุ่มเชื่อมโยงที่จะนำพาผู้ใช้เข้าสู่พื้นที่กรอกแบบฟอร์มประเมินเหตุการณ์และช่วงเวลาแบบเต็มรูปแบบ

### กลไกเส้นทางนำทางจริง (Exact Navigation Mechanism - Requires implementation validation)
* **สถานะการยืนยัน**: **ยังไม่มีการระบุหรืออนุมัติเส้นทาง URL หรือ Route แน่ชัดใน V1** 
* **ข้อจำกัดการอ้างอิง**: การระบุชื่อเส้นทาง `/timing` หรือสัญลักษณ์อื่นใดในเอกสารฉบับนี้เป็นเพียงการระบุเชิงตัวอย่าง (Illustrative Example) ประกอบความเข้าใจเท่านั้น **ยังไม่ใช่ข้ออนุมัติสำหรับสร้าง production route จริง และห้ามผู้พัฒนาทำการสร้าง route หรือเมนูถาวรจากข้อมูลในเอกสารนี้ล่วงหน้า**
* **กลไกที่ต้องทวนสอบในขั้นตอนพัฒนาโค้ดจริง**:
  * ความเหมาะสมของการใช้คอมโพเนนต์ร่วมภายใต้ Tab State เดิม
  * การแสดงผลแบบ Client-side subview (ไม่เปลี่ยน URL)
  * การขยาย Nested Route หรือการใช้ URL segment / query parameter เพื่อควบคุมสถานะการเปิดของหน้าจอย่อย โดยสอดคล้องกับประสิทธิภาพบนจอแคบและความหนาแน่นของเมนูเดิม

## 3. V1 View Structure (โครงสร้างหน้าจอ Strategic Timing V1)

หน้าจอ Full View ของ Strategic Timing V1 จะถูกออกแบบด้วยแนวคิด **Progressive Disclosure (การเปิดเผยข้อมูลทีละขั้น)** เพื่อควบคุมความซับซ้อน โดยแบ่งพื้นที่แสดงผลออกเป็น 4 ส่วนในหน้าเดียว (Single Page):

### 3.1 ส่วนกรอกข้อมูลเหตุการณ์ (Event Input Form - Progressive Phase 1)
* **พฤติกรรม**: แสดงผลตั้งแต่เริ่มต้น
* **ข้อมูลนำเข้า**: หัวข้อเหตุการณ์, หมวดหมู่, วันเวลา, ความยืดหยุ่น, ความเสี่ยงทางการเงิน และข้อจำกัดที่ทราบ
* **Loading State**: เมื่อผู้ใช้กดประเมิน จะแสดง Spinner และคำบรรยาย *"กำลังตรวจสอบเงื่อนไขความพร้อมและสัญญะจังหวะเวลา..."*
* **Empty State**: แสดงกล่องคำแนะนำ *"กรอกข้อมูลเหตุการณ์ด้านบนเพื่อเริ่มต้นวิเคราะห์ทางเลือกกลยุทธ์"*

### 3.2 ส่วนแสดงผลลัพธ์ (Assessment Results - Progressive Phase 2)
* **พฤติกรรม**: จะค่อย ๆ เลื่อนปรากฏขึ้นมาเมื่อประมวลผลเสร็จสิ้น
* **โครงสร้างการแสดงผล**:
  * **Today Timing Summary**: แสดงว่าจังหวะเวลาที่ผู้ใช้ระบุสอดคล้องกับภาพรวมของวันนี้อย่างไร
  * **Timing Window Results / Fixed Appointment Guidance**: แสดงช่วงเวลาที่เหมาะสมตามสัญญะเกิด หรือวิธีปฏิบัติหากวันเวลานั้นเปลี่ยนไม่ได้
  * **Strategic Action Translation**: แยกคำอ่านออกเป็น 3 เลเยอร์โปร่งใส (คำอ่านดาว, การตีความกลยุทธ์, ข้อเสนอแผนปฏิบัติ)
* **Error State**: แสดงกล่องสีเหลือง/แดงเมื่อข้อมูลบริบทสำคัญไม่ครบถ้วน เช่น *"ข้อมูลโซนเวลาหรือระดับความสำคัญไม่ถูกต้อง โปรดตรวจสอบข้อมูลนำเข้า"*

### 3.3 ส่วนจัดการแผนและบันทึกสะท้อนผล (Handoff Controls - Progressive Phase 3)
* **พฤติกรรม**: ปรากฏท้ายหน้าผลลัพธ์เพื่อส่งต่อข้อมูล
* **โครงสร้าง**:
  * **Planning Draft Preview**: ช่อง Text Area ที่ pre-fill คำแนะนำส่งต่อไปยัง Strategic Planning ผู้ใช้สามารถแก้ไขข้อความได้โดยอิสระ มีปุ่ม `[ส่งไปยังแผนกลยุทธ์]`
  * **Reflection Draft Preparation**: กล่องสรุปคำถามสะท้อนผลลัพธ์เพื่อเตือนให้กลับมาตอบ มีปุ่ม `[เตรียมร่างบันทึกสะท้อนคิด]`

### 3.4 ส่วนประวัติข้อมูล (Saved History - Base Area)
* **พฤติกรรม**: แสดงที่ด้านล่างสุดของหน้าจอเสมอ
* **โครงสร้าง**:
  * แสดงรายการผลประเมินเหตุการณ์ที่เคยบันทึกไว้ในอดีต (Saved Assessments) ในรูปแบบรายการสรุปสั้น
  * มีปุ่ม `[ลบประวัติ]` แยกแต่ละรายการ และปุ่ม `[ล้างข้อมูลทั้งหมด]` ในจุดที่ปลอดภัย

## 4. Event Decomposition Decision (หลักการกักแยกและสลายเหตุการณ์)

เหตุการณ์ในโลกความเป็นจริงมักทับซ้อนและมีความเสี่ยงหลายด้านเกิดขึ้นพร้อมกัน เพื่อป้องกันไม่ให้คำแนะนำเกิดการปะปนหรือใช้ฤกษ์ยามชดเชยข้อขัดข้องทางกฎหมาย/การเงิน ระบบ V1 จึงบังคับใช้หลักการ **"หนึ่งเหตุการณ์จริง สามารถแยกเป็นหลายใบประเมินผลสัมฤทธิ์ (Event Decomposition)"**

### ตัวอย่างกรณีศึกษาเชิงแนวคิด
**เหตุการณ์จริง**: คุณตั้มต้องเดินทางไปพบพาร์ทเนอร์ที่ต่างจังหวัดเพื่อพูดคุยโปรเจกต์ใหม่และโอนเงินลงทุนก้อนแรก

ระบบจะแนะนำให้สลายกิจกรรมออกเป็น 4 ใบประเมินผลแยกจากกัน ดังนี้:
1. **Assessment A (Travel)**: ประเมินจังหวะเวลาการเดินทางเพื่อความปลอดภัย การลดความเหนื่อยล้าสะสม และการสำรองเวลาการเดินทางจริง
2. **Assessment B (Negotiation)**: ประเมินจังหวะการเจรจาขอบเขตหน้าที่และผลประโยชน์ เพื่อจำกัดความเร่งรีบในการตอบรับเงื่อนไข
3. **Assessment C (Project Start)**: ประเมินความสอดคล้องของโปรเจกต์กับจุดแข็ง และประเมินทรัพยากรบุคคล/ขอบข่ายงานก่อนเริ่มงานจริง
4. **Assessment D (Payment)**: ตรวจสอบความพร้อมของเอกสารสัญญา ความคุ้มครองสภาพคล่องขั้นต่ำ และการแยกช่วงเวลาพูดคุยออกจากการโอนเงินจริง

## 7. Fixed Appointment Contract & Guidance Flow (กรณีนัดหมายที่เปลี่ยนวันเวลาไม่ได้)

หาก `timeFlexibility` ถูกกำหนดค่าเป็น `Date and time fixed` ระบบจะระงับการค้นหาฤกษ์มงคล และเปลี่ยนสถานะเข้าสู่ **"Fixed Appointment Mode (โหมดการจัดการความเสี่ยงนัดหมายคงที่)"** โดยมีกระบวนการแสดงผลเชิงกลยุทธ์เพื่อจัดสรรแนวทางการดำเนินงานดังนี้:

### ลำดับขั้นตอนการดำเนินงานเชิงแนวคิด (Operational Flow)
1. **จำกัดขอบเขตของกิจกรรม (De-risking Boundaries)**:
   * แยกขั้นตอนการเจรจาหรือทำความเข้าใจ ออกจากขั้นตอนการลงนามหรือการโอนเงินทันทีในนัดหมาย
2. **การจัดลำดับเนื้อหาพูดคุย (Agenda Sequencing)**:
   * ระบุประเด็นที่ควรเปิดโต๊ะพูดคุยก่อนเพื่อสร้างความเข้าใจร่วม (เช่น ทบทวนข้อเท็จจริงในอดีต)
   * ระบุประเด็นที่ควรผลักออกไปตัดสินใจในรอบหน้าหลังจากนำข้อมูลกลับมาทบทวนหลังบ้าน
3. **การทบทวนและสำรองความเสี่ยงด้านการตัดสินใจ (Cooling-off Suggestion)**:
   * แสดงข้อความเตือนความชวนคิด: *"แนะนำให้มีระยะเวลาทบทวนเอกสารสัญญาอย่างน้อย 24 ชั่วโมงก่อนทำการยืนยันหรือลงนามใด ๆ"*
4. **ความพร้อมด้านหลักฐาน (Evidence and Verification Checklist)**:
   * รายการตรวจสอบเอกสารและข้อตกลง และการระบุพาร์ทเนอร์ร่วมวิเคราะห์ (เช่น ฝ่ายบัญชี หรือผู้เกี่ยวข้องหลัก)
5. **บันทึกความเข้าใจร่วม (Written Acknowledgement)**:
   * กำหนดให้ส่งอีเมลสรุปบันทึกการประชุม (Meeting notes) ทันทีหลังนัดหมายเสร็จสิ้นเพื่อยืนยันคำเข้าใจที่ตรงกัน

## 8. Local Persistence Contract (สัญญาการจัดเก็บข้อมูลภายในเครื่อง)

เพื่อความปลอดภัยของข้อมูลส่วนตัวและระบบเก็บข้อมูลแบบ Local-first:
* **กลไกการจัดเก็บ**: บันทึกข้อมูลลงใน LocalStorage ของเบราว์เซอร์
* **การเสนอใช้คีย์จัดเก็บข้อมูล (Storage Keys)**:
  * คีย์เก็บข้อมูลโครงการและกิจกรรมประเมินทั้งหมด: `astro:strategic-timing:events:v1` (เก็บเป็นกล่องข้อความระดับบนสุด)
  * คีย์เก็บค่าตั้งค่าคอนฟิกูเรชัน: `astro:strategic-timing:settings:v1`
  * *ข้อตกลงสำหรับข้อมูลร่าง*: ข้อมูลร่างแบบฟอร์ม (Drafts) จะถูกเก็บไว้ภายใน Event หรือ Assessment object ที่ยังไม่ยืนยันเท่านั้น **โดยไม่มีการจัดตั้งคีย์ Drafts แยกต่างหากใน V1**
* **โครงสร้างการเก็บข้อมูลแบบมีเวอร์ชัน (schemaVersion & Serialization)**:
  * **schemaVersion**: กำหนดเวอร์ชันโครงสร้างข้อมูลภายใน data envelope เสมอ (เช่น `version: "1.0"`)
  * **JSON validation**: ทวนสอบประเภทข้อมูลและโครงสร้าง JSON เสมอเมื่อทำการโหลด
  * **timezone preservation**: ต้องเก็บข้อมูล Timezone ดั้งเดิมของ Event ไว้โดยไม่มีการบิดเบือนเวลา
  * **date serialization**: ข้อมูลวันที่และเวลาทั้งหมดจะถูกจัดเก็บในรูปแบบ ISO 8601 string
  * **duplicate ID handling**: ป้องกันรหัส ID ซ้ำซ้อนด้วยการตรวจเช็กคีย์ก่อนทำการ insert หากพบ ID ซ้ำให้ปฏิเสธการทำรายการ
  * **SSR-safe load concept**: โหลดข้อมูลฝั่ง Client-side เท่านั้นหลังจากคอมโพเนนต์ React ทำการ Mount เรียบร้อย หลีกเลี่ยงการเรียกใช้งาน window/localStorage ระหว่างขั้นตอน Server-Side Rendering (SSR)
  * **safe in-memory fallback**: หาก localStorage ล้มเหลวหรือถูกระงับ ให้ใช้งานผ่าน in-memory state ชั่วคราวแทน
* **เพดานการจัดเก็บและจำกัดขีดความสามารถ (V1 Capacity Contract)**:
  * **maximumEvents**: จำกัดการจัดเก็บ Event ระดับบนสุดได้สูงสุด **100 Events** (Event คือ container ระดับบน)
  * **maximumAssessmentsPerEvent**: จำกัดใบประเมินผลจังหวะเวลา (Assessment) ได้สูงสุด **5 Assessments per Event**
  * **maximumTotalAssessments**: ขอบเขตเพดานการวิเคราะห์รวมสูงสุดทางอ้อม (derived upper bound) อยู่ที่ **500 Assessments**
  * *การแบ่งแยกหน่วยประเมิน*: Event และ Assessment ถือเป็นโครงสร้างคนละหน่วยความจุ ห้ามใช้คำว่า "50 assessments" หรือหน่วยนับแบบเหมารวมแทนเพดาน Event ความจุ 100 Events
* **ข้อพึงระวังและการจัดการพื้นที่จัดเก็บ (No Automatic Pruning & Deletion)**:
  * **ห้ามลบข้อมูลเก่าอัตโนมัติ (Automatic Pruning is Prohibited)**: ระบบห้ามทำการลบรายการหรือล้างข้อมูลเก่าใด ๆ (ไม่มีการใช้ FIFO/oldest-item deletion) เมื่อพื้นที่จัดเก็บเข้าใกล้หรือถึงระดับเพดานสูงสุด
  * **มาตรการลดความสูญเสียข้อมูล**: เมื่อชนเพดานการจัดเก็บ ระบบต้องบังคับให้ผู้ใช้มีส่วนร่วมตัดสินใจสั่งการทำลายข้อมูลด้วยตนเอง (User controls destructive action) โดยแสดงตัวเลือก: ลบ Event ที่ไม่ต้องการ / Export ข้อมูลดิบออก / ยกเลิกการประเมิน
  * **การยืนยันการลบแบบปลอดภัย**: การลบข้อมูล Event หรือข้อมูลใด ๆ ต้องผ่าน Modal ยืนยันสิทธิ์สองครั้งอย่างชัดเจน (Explicit Confirmation)
  * **การคุ้มครองข้อมูลการเชื่อมโยง**: ข้อมูลที่ผู้ใช้เคยส่งออกไปส่งต่อให้แผนกลยุทธ์ (Strategic Planning) หรือสะท้อนคิด (Reflection Log) สำเร็จแล้ว ต้องไม่ถูกลบตามหลังเมื่อทำการสั่งลบ Event ต้นทาง
  * **รูปแบบพฤติกรรมการควบคุมความจุ (Capacity Behavior Flow)**:
    ```text
    Stored Events < 90
    → Operate normally (ใช้งานปกติ)

    Stored Events 90–99
    → Show approaching-capacity warning (แสดงคำแจ้งเตือนเข้าใกล้เพดาน)

    Stored Events = 100
    → Block creation of a new Event (บล็อกการสร้าง Event ใหม่)
    → Offer Delete / Export / Cancel (เสนอทางเลือก ลบ / ส่งออก / ยกเลิก)
    → Never auto-delete existing data (ห้ามลบข้อมูลเดิมอัตโนมัติ)
    ```
* **กลไกการกู้คืนและการจัดการข้อมูลที่เสียหาย (Error Recovery Contract)**:
  * **ห้ามล้างข้อมูลที่เสียหายโดยอัตโนมัติ (No Automatic Deletion of Corrupted Data)**: ระบบต้องไม่มีการสั่งลบหรือเขียนทับข้อมูลดิบที่อ่านไม่ได้โดยพละการเพื่อป้องกันการสูญหายของข้อมูลโดยไม่ได้ตั้งใจ (Never lose original user data automatically)
  * **ห้ามเขียนทับ Payload ดิบที่เสียหาย (No Overwrite of Raw Corrupted Payload)**: หากกระบวนการแปลงข้อมูล (Parsing) หรือการโยกย้ายข้อมูล (Migration) ล้มเหลว ให้ใช้ข้อมูลโครงสร้างเปล่าในหน่วยความจำชั่วคราว (Temporary empty in-memory state) โดยไม่มีการบันทึกทับลงใน Storage จริง
  * **การแจ้งเตือนผู้ใช้งาน (User Alerting)**: แสดงกล่องข้อความแจ้งเตือนผู้ใช้งานเมื่อตรวจพบข้อมูลที่อ่านไม่ได้เพื่อให้รับทราบสถานะระบบ
  * **การล้างข้อมูลแบบควบคุมความปลอดภัย**: ปุ่มล้างข้อมูลทั้งหมดหรือล้างคีย์ที่เสียหายจะต้องผ่านกระบวนการยืนยันสิทธิ์สองครั้งอย่างชัดเจน (Explicit Confirmation)
  * **การรักษาข้อมูลดิบเพื่อกู้คืน (Preserve Raw Payload)**: จัดเก็บและคงสภาพดิบของข้อมูลเดิมไว้เพื่อให้ผู้ใช้งานสามารถดึงข้อมูลเดิม (Raw export) หรือแก้ไขด้วยเครื่องมือกู้คืนได้ภายนอก
  * **การสำรองข้อมูล (Backup before migration)**: หากมีการโยกย้ายเวอร์ชันข้อมูลหรือแปลงโครงสร้างข้อมูลในอนาคต ต้องสร้างสำรองข้อมูล (Backup snapshot) ของโครงสร้างข้อมูลเดิมก่อนทำการเปลี่ยนแปลงเสมอ โดยไม่เขียนทับโครงสร้างใหม่ทับของเดิมโดยไม่มีการ backup
  * **ลำดับขั้นตอนการกู้คืนข้อมูล (Recovery Flow Diagram)**:
    ```text
    Read stored payload
    → Validate schema and JSON
    → If valid: load normally
    → If invalid: preserve raw payload
    → Enter recovery state
    → Offer Retry / Export raw data / Confirmed Reset
    ```

## 9. Handoff Contracts (การส่งต่อข้อมูลเชื่อมโยงระบบหลัก)

การส่งต่อข้อมูลการประเมินกลยุทธ์ไปยังฟีเจอร์เดิมของ WorkOS-Lite จะต้องปฏิบัติตามหลักจริยธรรมข้อมูลอย่างเคร่งครัด:

### 9.1 การส่งข้อมูลไปยังแผนกลยุทธ์ (Strategic Planning Handoff)
* **ปลายทาง**: ฟิลด์เป้าหมายในบันทึกแผนงานเดิม ได้แก่ `Focus Next`, `Slow Down`, `Next Small Action`, และ `Review Later`
* **นโยบายความปลอดภัย**:
  * **ห้ามเขียนทับข้อมูลเดิมโดยเด็ดขาด (No Automatic Overwrite)**
  * ระบบจัดเตรียมกล่อง Preview Text Area ให้ผู้ใช้ทวนสอบและแก้ไขข้อมูลคำแนะนำเชิงกลยุทธ์
  * ใช้วิธีต่อท้ายข้อมูลเดิม (Append-only) โดยใส่หัวข้อบ่งบอกที่มาอย่างชัดเจน เช่น:
    `[Strategic Timing - 15/07/2026]: เตรียมสแกนเอกสารสัญญา Green Fineness ก่อนนัดเจรจา`
  * การกดปฏิเสธหรือยกเลิก (Cancel) จะต้องไม่เกิดความเปลี่ยนแปลงใด ๆ ต่อฟิลด์แผนงานเดิม

### 9.2 การส่งข้อมูลไปยังบันทึกสะท้อนคิด (Reflection Log Handoff)
* **ปลายทาง**: สร้างแบบบันทึกสะท้อนคิดร่างชั่วคราว (Reflection Entry Draft) แนบกับกิจกรรมที่ประเมินเสร็จสิ้น
* **ชุดคำถามสะท้อนผลสัมฤทธิ์**:
  * *"กิจกรรมเกิดขึ้นภายในช่วงเวลาที่ประเมินไว้หรือไม่ และผลลัพธ์เปรียบเทียบในโลกจริงเป็นอย่างไร?"*
  * *"เกิดข้อขัดข้องด้านเวลา หรือเกิดเงื่อนไขความพร้อมใดที่เปลี่ยนแปลงไปจากแผนตั้งต้น?"*
  * *"มีการตัดสินใจเรื่องสำคัญภายใต้ความเร่งรีบหรือแรงกดดันเชิงเวลาหรือไม่?"*
  * *"มีปัจจัยภายนอกใดเกิดขึ้นที่ระบบไม่สามารถประเมินได้ล่วงหน้า?"*

## 10. Confidence and Uncertainty Vocabulary (กรอบคำศัพท์ระบุความเชื่อมั่น)

ระบบ Strategic Timing จะ **ไม่แสดงคะแนนร้อยละ (%) หรือคะแนนตัวเลขชี้ขาดเด็ดขาดในการประเมินฤกษ์** แต่จะใช้กรอบการอธิบายเชิงคุณภาพเพื่อสะท้อนความครบถ้วนของข้อมูลบริบทธุรกิจ:

* **Higher Context (ข้อมูลประกอบระดับสูง)**:
  * *ความหมาย*: ข้อมูลประวัติ ข้อจำกัด งบประมาณ โซนเวลา และข้อมูลสัญญะเกิดของผู้ใช้หลักและผู้ร่วมเหตุการณ์ครบถ้วนตามหลักเกณฑ์
* **Moderate Context (ข้อมูลประกอบระดับปานกลาง)**:
  * *ความหมาย*: ข้อมูลบางมิติยังไม่ชัดเจน หรือไม่ได้ระบุข้อจำกัดเวลาและบริบทเป้าหมายงานอย่างละเอียด
* **Limited Context (ข้อมูลประกอบระดับจำกัด)**:
  * *ความหมาย*: ระบุเพียงวันและช่วงเวลา โดยไม่มีข้อมูลเหตุการณ์จริงหรือบริบททางโลกประกอบการประเมิน

## 11. High-Stakes Decision Handling (การจัดการกิจกรรมที่มีความเสี่ยงสูง)

กิจกรรมจะถูกจำแนกเป็น **"ความเสี่ยงระดับสูง (High-stakes)"** เมื่อเข้าเกณฑ์ประการใดประการหนึ่ง:
1. การทำธุรกรรมทางการเงินหรือให้กู้ยืมเงินเกินกว่ามูลค่าที่กำหนด
2. กิจกรรมที่ส่งผลผูกพันทางกฎหมายถาวรที่ไม่อาจยกเลิกหรือกู้คืนได้ง่าย (Irreversible decisions)
3. กิจกรรมที่มีความสอดคล้องกับพฤติกรรมพึ่งพิงโชคชะตาจนอาจทำให้ขาดวิจารณญาณทางธุรกิจ

### มาตรการคุ้มครอง (Mitigation Rules)
* **สัญลักษณ์เตือนภัย**: แสดงแถบสีเตือนสีเหลืองสะท้อนคิดอย่างเด่นชัดบนหน้าจอ
* **บังคับขั้นตอนทวนสอบ**: เสนอรายการประเมินความเสี่ยงและสภาพคล่องทางเงิน (เช่น ปริมาณเงินสำรองหลังโอน)
* **ชะลอการตัดสินใจ**: เสนอให้ผู้ใช้เว้นช่วงระยะเวลา 24-48 ชั่วโมงก่อนการสรุปตัดสินข้อตกลงเพื่อทบทวนผลงาน

---

## 12. Candidate Date Comparison (การประเมินและเปรียบเทียบช่วงเวลา)

* **ขีดจำกัดการใช้งาน**: สนับสนุนการกรอกเปรียบเทียบวันและจังหวะเวลาสำหรับเหตุการณ์เดียวกันได้ **สูงสุด 3 ตัวเลือก (Max 3 candidate dates)**
* **รูปแบบรายงาน**: แสดงตารางเปรียบเทียบในลักษณะด้านต่อด้าน (Side-by-side)
* **เนื้อหาเปรียบเทียบ**: แสดงระดับความเหมาะสมตามเลเยอร์สัญญะ ข้อดี ข้อควรระวัง และข้อจำกัดทางกายภาพเด่นของแต่ละวัน เพื่อให้ผู้ใช้มองเห็นทางเลือกประกอบการตัดสินใจได้รอบด้านที่สุด

---

## 13. Data Retention and Deletion (นโยบายการจัดเก็บและล้างข้อมูล)

* **นโยบาย Data Retention**: ข้อมูลรายการประเมินจังหวะเวลาจะถูกเก็บไว้ตราบเท่าที่ผู้ใช้งานไม่ได้สั่งล้างระบบ
* **นโยบายการลบข้อมูล (Deletion behavior)**:
  * ผู้ใช้งานสามารถสั่งลบผลการประเมินรายตัวได้ทันที โดยไม่มีการเก็บแคชย้อนหลัง
  * ระบบติดตั้งปุ่ม `[ล้างประวัติการประเมินเวลาทั้งหมด]` ที่ด้านล่างสุดของ Saved Assessments
  * การสั่งล้างข้อมูลทั้งหมดจะต้องแสดง Modal Double-Confirmation ยืนยันสิทธิ์สองครั้งเพื่อป้องกันการกดพลาด และไม่มีผลไปลบข้อมูลบันทึกใน Strategic Planning หรือ Reflection History เดิม

---

## 14. Acceptance Criteria (เกณฑ์การประกันคุณภาพเอกสารและแผนงาน)

ตั๋วการออกแบบระบบ Strategic Timing V1 จะได้รับสิทธิ์ผ่านการตรวจรับรองคุณภาพเมื่อผ่าน 5 ข้อกำหนด:
1. เอกสารนิยาม Decision Resolution และ QA Plan ได้รับการสร้างและลงทะเบียนข้อมูลครบถ้วน
2. โครงสร้าง JSON Data Contracts ของ Event Input และ Timing Result ได้รับการออกแบบโดยปราศจากโค้ดโปรแกรม
3. มีการออกแบบกรอบจำกัดสิทธิ์ความปลอดภัยจริยธรรมข้อมูล และ Exclusions ครบถ้วนตามมาตรฐาน ASTRO-REAL-APP-001/002
4. มีการจัดระเบียบนโยบายส่งต่อข้อมูลเชื่อมโยง (Handoffs) แผนสำรองข้อมูลแมนนวล และการห้ามทำ Scoring algorithms
5. ผ่านการตรวจสอบประเมินความสอดคล้อง (QA checklist) และได้รับความเห็นชอบอนุมัติจากผู้ใช้หลัก (User Approval Gate)
