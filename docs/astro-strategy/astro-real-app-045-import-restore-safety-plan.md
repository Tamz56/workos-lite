# ASTRO-REAL-APP-DEV-045 — Import / Restore Safety Plan

เอกสารแผนยุทธศาสตร์ความมั่นคงปลอดภัยของการนำเข้าและกู้คืนข้อมูล (Import / Restore Safety Plan) สำหรับ Astro Real App MVP-v3

---

## 1. Goal (เป้าหมาย)

ออกแบบกลไกและข้อกำหนดด้านความปลอดภัยขั้นสูงสุดในการนำเข้าและกู้คืนข้อมูล (Import & Restore) จากไฟล์สำรองข้อมูล JSON เข้าสู่ระบบ LocalStorage ของเบราว์เซอร์ เพื่อป้องกันข้อผิดพลาดในการเขียนทับข้อมูลประวัติสะสมโดยไม่ได้ตั้งใจ (Overwrite Prevention) ตรวจสอบโครงสร้างข้อมูลที่อาจชำรุดเสียหาย (Schema Validation) และจำกัดขอบเขตการเข้าถึงข้อมูลของระบบอย่างรัดกุม โดยเอกสารนี้มีวัตถุประสงค์เพื่อเป็นพิมพ์เขียว (Blueprint) เชิงทฤษฎีก่อนเริ่มอิมพลีเมนต์จริงในเฟสถัดไป

---

## 2. Scope & Non-Scope (ขอบเขตและขอบเขตนอกเหนืองาน)

### ขอบเขตการทำงาน (Scope)
1. วิเคราะห์ความเสี่ยงของการเขียนข้อมูล (Write-Heavy Operation) เปรียบเทียบกับการอ่านข้อมูล
2. กำหนดโครงสร้างสกีมาของไฟล์ JSON สำรองข้อมูลที่ระบบยอมรับ (Accepted JSON Envelope)
3. กำหนดมาตรการการตรวจสอบ Metadata และ Payload Schema อย่างละเอียด
4. กำหนดกระบวนการจำลองข้อมูลจำลองล่วงหน้าแบบปลอดภัย (Import Dry Run / Preview)
5. กำหนดเกณฑ์การวิเคราะห์และตรวจสอบข้อขัดแย้งของข้อมูล (Conflict Detection Rules)
6. กำหนดขอบเขตคีย์ที่อนุญาตให้เขียนทับ (Allowed Keys) และคีย์ที่ห้ามเขียนทับโดยเด็ดขาด (Never Restored Keys)
7. เสนอกลยุทธ์การย้อนกลับสถานะเดิมเมื่อเกิดข้อผิดพลาด (Rollback Strategy)
8. วางแผนตรวจสอบคุณภาพและการทดสอบด้วยตนเอง (Manual QA Plan)

### ขอบเขตนอกเหนืองาน (Non-Scope)
- **ห้ามแก้ไขโค้ดการทำงานจริง (Runtime Code)** หรือปรับปรุงหน้าจอผู้ใช้ (UI) สำหรับการสั่งนำเข้าข้อมูลในเฟสนี้
- ไม่เขียนข้อมูลหรือเปลี่ยนค่าคีย์ LocalStorage ใด ๆ ในเครื่องจริงระหว่างการร่างแผนนี้
- ไม่เพิ่มสิทธิ์หรือขยายขอบเขตการเขียนข้อมูลไปยังโดเมนหรือ Namespace อื่นนอกเหนือจาก `astro-real-app:*`

## 3. Why Import/Restore is Higher Risk than Export (ทำไมการกู้คืนจึงมีความเสี่ยงสูงกว่าการส่งออก)

การส่งออกข้อมูล (Export/Backup) เป็นการทำงานแบบ **อ่านอย่างเดียว (Read-Only)** ซึ่งแทบไม่มีความเสี่ยงต่อความสมบูรณ์ของระบบจัดเก็บหลัก แต่การนำเข้าและกู้คืน (Import/Restore) เป็นการทำงานแบบ **เขียนทับ (Write-Heavy)** ที่มีความเสี่ยงสูงมากดังนี้:
1. **อุบัติเหตุข้อมูลสูญหาย (Accidental Data Overwrite)**: การกู้คืนข้อมูลชุดใหม่อาจไปเขียนทับข้อมูลดิบสะสมดั้งเดิม (เช่น บันทึกประวัติการสะท้อนคิดสะสมรายสัปดาห์หรือรายเดือน) ซึ่งทำให้ประวัติเก่าที่ผู้ใช้สะสมไว้หายไปอย่างถาวร
2. **ข้อมูลภายในชำรุดเสียหาย (Data Corruption)**: หากผู้ใช้นำเข้าไฟล์ JSON ที่มีสกีมาไม่ถูกต้อง ข้อมูลที่เสียหายอาจทำให้ระบบวิเคราะห์ (Today, Weekly, Monthly Engine) ประสบสภาวะขัดข้อง (Crash) หรือแอปพลิเคชันค้าง
3. **ปัญหาความเข้ากันได้ต่างรุ่น (Version Incompatibility)**: ไฟล์สำรองข้อมูลอาจถูกส่งออกด้วยโครงสร้างรุ่นเก่า หรือถูกดัดแปลงมือ ซึ่งการดึงข้อมูลมาแปลงค่าโดยไม่มี Schema check จะส่งผลต่อความคงเส้นคงวาของแอปพลิเคชัน

## 5. Required Metadata & Schema Validation (ระบบตรวจสอบความถูกต้อง)

ก่อนการนำข้อมูลเขียนลงในระบบจัดเก็บจริง ระบบจะต้องรันโปรแกรมตรวจสอบ 2 ชั้นแบบทันที (Atomic Gatekeeper):

### ก. Metadata Validation (ตรวจสอบข้อมูลเชิงควบคุม)
1. ตรวจสอบคุณลักษณะ `$schema` ในระดับราก (Root) ต้องตรงกับ `"https://arbor-desk.com/schemas/astro-strategy-backup-v1.json"` เสมอ
2. ตรวจสอบ `metadata.appName` ต้องตรงกับ `"Astro Strategy Lab"` เสมอ
3. ตรวจสอบ `metadata.exportVersion` ต้องไม่เกินเวอร์ชันปัจจุบันที่ระบุในซอร์สโค้ด (เช่น เวอร์ชัน `1`)

### ข. Payload Schema Validation (ตรวจสอบโครงสร้างข้อมูลตามรายคีย์)
1. **Birth Profile**:
   - ต้องผ่านการตรวจสอบความถูกต้องด้วยกลไกเดียวกับ `validateAstroBirthProfile`
   - ต้องตรวจสอบรูปแบบวันเกิดเป็น `YYYY-MM-DD` และเวลาเกิดเป็น `HH:mm` (00:00 - 23:59)
   - ฟิลด์แสดงผล `displayName` และสถานที่เกิด `birthPlace` ต้องไม่เป็นค่าว่างเปล่า
2. **Reflection History**:
   - ฟิลด์ `data` ภายใต้คีย์ประวัติสะสมต้องเป็น Array เสมอ (หากว่างเปล่าให้จัดเก็บเป็น Array เปล่า `[]`)
   - แต่ละรายการย่อยใน Array ต้องมีฟิลด์หลักครบถ้วนตาม `ReflectionHistoryItem` เช่น `id`, `reflectionDate` (ในฟอร์แมต YYYY-MM-DD), `noticedNotes`, และออบเจกต์ย่อย `dailyCheckinSnapshot`
3. **Planning Notes**:
   - โครงสร้างวัตถุต้องสอดคล้องกับคลาสประเภท `AstroPlanningNotes` (มีฟิลด์ `focusNext`, `slowDown`, `nextSmallAction`, `reviewLater`)
4. **Onboarding Status**:
   - ตรวจสอบฟิลด์ `isDismissed` ต้องเป็น Boolean

*หากมีข้อมูลคีย์ตัวใดตัวหนึ่งไม่ผ่านเกณฑ์การทดสอบข้างต้น (Validation failed) ระบบจะทำการปฏิเสธไฟล์ทั้งหมดในระดับ Transaction ทันที (All-or-Nothing Rule)*

## 6. File Source and Privacy Warning (ความเป็นส่วนตัวและความปลอดภัยของแหล่งที่มาไฟล์)

- **การระวังแหล่งที่มาไฟล์ (File Source Warning)**: 
  เนื่องจากไฟล์สำรองข้อมูล JSON เป็นไฟล์ข้อความแบบเปิด (Plain text) ที่อาจแก้ไขด้วยมือได้ ระบบต้องแสดงคำเตือนผู้ใช้เด่นชัด:
  > *“คำเตือน: โปรดนำเข้าไฟล์สำรองข้อมูลที่ดาวน์โหลดมาจากตัวแปรระบบพรีวิวนี้เท่านั้น การอัปโหลดไฟล์ที่ถูกดัดแปลงโครงสร้างภายนอก หรือนำเข้าจากแหล่งที่ไม่รู้จัก อาจส่งผลให้ระบบคำนวณและเก็บข้อมูลเสียหาย”*
- **การรักษาข้อมูลส่วนบุคคล (PII/Privacy)**:
  เนื่องจากข้อมูลส่วนตัว (เช่น วัน เวลา สถานที่เกิด และบันทึกความคิดเห็น) เป็นข้อมูลที่มีความสำคัญต่อความเป็นส่วนตัว ระบบต้องเตือนให้ระมัดระวังในการแชร์ไฟล์ หรือแสดงหน้าจอยืนยันเพื่อชี้แจงว่าระบบไม่ได้เก็บไฟล์นี้ไว้บนระบบคลาวด์/เซิร์ฟเวอร์ใด ๆ แต่เป็นการประมวลผลฝั่งเบราว์เซอร์ผู้ใช้งานโดยตรง

## 7. Import Dry Run / Preview Requirement (การสแกนและรายงานผลลัพธ์จำลอง)

เมื่อผู้ใช้ทำการอัปโหลดไฟล์ JSON ระบบกู้คืนข้อมูลจะไม่เขียนลงหน่วยความจำทันที แต่จะเข้าสู่โหมด **Dry Run วิเคราะห์ข้อมูลล่วงหน้า** และแสดงผลเป็น Dashboard สรุปความพร้อมบนหน้าจอ UI:
- **ข้อมูลจำลองที่จะรายงานต่อผู้ใช้งาน**:
  - **ชื่อโปรไฟล์ในไฟล์สำรอง**: (เช่น *"พบโปรไฟล์ดวงเกิดของคุณ: คุณตั้ม"*)
  - **จำนวนประวัติสะท้อนคิด**: (เช่น *"พบประวัติสะสม 15 บันทึก"*)
  - **วันเวลาที่ส่งออกไฟล์**: (เช่น *"ไฟล์นี้สำรองข้อมูลไว้เมื่อ 2026-06-08 22:00"*)
  - **การตรวจจับประวัติซ้ำซ้อน**: รายงานจำนวนประวัติสะสมที่มีอยู่ในไฟล์ที่มีรหัส `id` หรือวันที่ซ้ำซ้อนกับในเบราว์เซอร์ปัจจุบัน เพื่อเตรียมความพร้อมในการกู้คืนในโหมดผสาน

## 8. Conflict Detection & Resolution Rules (การตรวจสอบและจัดการข้อขัดแย้งของข้อมูล)

เพื่อไม่ให้ประวัติที่จดบันทึกไว้ในเครื่องเบราว์เซอร์เดิมถูกเขียนทับอย่างผิดปกติ แผนความปลอดภัยกำหนดเงื่อนไขการตรวจสอบข้อขัดแย้งเชิงตรรกะดังนี้:

### ก. การขัดแย้งของโปรไฟล์ดวงเกิด (Birth Profile Conflict)
- ระบบจะตรวจเช็คว่าฟิลด์ `displayName`, `birthDate`, หรือ `birthTime` ในไฟล์สำรองแตกต่างไปจากโปรไฟล์ดวงเกิดที่เซฟไว้ในระบบปัจจุบันหรือไม่
- หากตรวจพบความแตกต่าง ระบบจะขึ้นไอคอนเตือนความขัดแย้งและอธิบายแก่ผู้ใช้ว่าการกู้คืนจะเปลี่ยนแกนดวงปัจจุบัน ซึ่งจะทำให้ Today Engine เปลี่ยนแปลง

### ข. การขัดแย้งของคีย์ประวัติการสะท้อนคิด (Reflection History Conflict)
- รายการบันทึกในอาเรย์ที่มีค่าไอดี `id` หรือวันจดบันทึก `reflectionDate` ตรงกัน ถือเป็นข้อมูลขัดแย้ง
- **นโยบายแก้ไข (Resolution Policy)**: 
  - ในโหมดผสานปลอดภัย (Merge-Safe) ระบบจะคงประวัติที่มีการอัปเดตล่าสุด (`updatedAt` ที่ใหม่กว่า) ไว้ หรือยึดประวัติในเครื่องปัจจุบันเป็นหลัก
  - ในโหมดเขียนทับทั้งหมด (Replace) ข้อมูลในไฟล์สำรองจะลบล้างประวัติเดิมในเบราว์เซอร์ออกไปทันที

### ค. กฎการปกป้องคีย์เดิมในระบบ (Existing Key Protection Rules)
- ข้อมูลที่มีรหัสคีย์นอกเหนือขอบเขตเป้าหมาย รวมถึงคีย์ของระบบเก่าดั้งเดิม (เช่น `astro-strategy:*`, `astro.strategy.*`) หรือคีย์ทั่วไปของเบราว์เซอร์ จะไม่ถูกแตะต้องและถูกกรองทิ้งออกจากขั้นตอนการอ่านข้อมูลในไฟล์ JSON ทันที เพื่อรับประกันว่าการนำเข้าข้อมูลจะไม่มีผลกับระบบโปรโตไทป์เดิมหรือระบบอื่นเด็ดขาด

## 9. Suggested Restore Modes (โหมดการกู้คืนข้อมูลที่แนะนำ)

การนำเข้าข้อมูลจะช่วยอำนวยความสะดวกให้ผู้ใช้งานจัดการข้อมูลของตนเองได้ยืดหยุ่นผ่าน 3 โหมดทำงานหลัก:

### 1) Preview Only / Dry-Run (โหมดจำลองพรีวิววิเคราะห์ข้อมูล)
- เป็นค่าเริ่มต้น (Default Mode) หลังจากเลือกไฟล์
- ตรวจสอบความถูกต้องและแจกแจงรายละเอียดสถิติเปรียบเทียบ โดยไม่มีการเขียนลง LocalStorage
- ช่วยให้ผู้ใช้วิเคราะห์ขนาดและข้อมูลที่จะเปลี่ยนไปได้ปลอดภัย 100%

### 2) Merge-Safe Mode (โหมดผสานประวัติแบบปลอดภัย - *Recommended*)
- **ตรรกะการทำงาน**:
  - นำเข้าและผสานเฉพาะรายการบันทึกประวัติสะสม (`ReflectionHistoryItem`) ที่ยังไม่มีอยู่ใน LocalStorage ปัจจุบัน
  - หาก `id` หรือวันที่ตรงกัน จะคงค่าเดิมของเครื่องท้องถิ่นไว้เพื่อความปลอดภัย
  - สำหรับข้อมูลดราฟต์และแผนเชิงกลยุทธ์ หากในระบบปัจจุบันมีข้อมูลอยู่แล้ว จะข้ามการกู้คืนเพื่อไม่ให้เขียนทับงานที่พิมพ์ค้างอยู่
- **เป้าหมาย**: เพิ่มข้อมูลประวัติเดิมที่ขาดหายเข้าด้วยกันโดยไม่ทำลายข้อมูลปัจจุบัน

### 3) Replace Mode (โหมดล้างและเขียนทับทั้งหมด)
- **ตรรกะการทำงาน**:
  - เขียนทับคีย์จัดเก็บของ Astro Real App ทั้ง 5 คีย์ด้วยค่าจากไฟล์สำรองข้อมูลโดยตรง
- **เกณฑ์ความปลอดภัยสูง (Explicit Confirmation)**:
  - ผู้ใช้งานต้องทำเครื่องหมายยืนยันความเสี่ยงบน UI (เช่น Checkbox ยอมรับการเขียนทับ)
  - ต้องแสดงกล่องยืนยันการทำรายการของเบราว์เซอร์ (Browser confirm dialog) ซ้ำอีก 1 รอบเพื่อตรวจสอบสติการกู้คืนของผู้ใช้

## 11. Rollback & Pre-Restore Backup Strategy (กลยุทธ์กู้คืนสภาพเดิม)

เพื่อลดความเสี่ยงสูงสุดกรณีการเขียนข้อมูลล้มเหลว (เช่น อัปโหลดไฟล์ขนาดใหญ่เกินจนส่งผลให้เบราว์เซอร์เกิด Error โควต้าเต็ม - `QuotaExceededError`):

1. **Rollback Buffer (ตัวสำรองชั่วคราว)**:
   ก่อนเริ่มรันกระบวนการเขียนทับลง LocalStorage ระบบจะทำการอ่านข้อมูลดิบปัจจุบันทั้งหมดในเครื่อง แล้วบันทึกสำรองลงในหน่วยความจำชั่วคราว (Memory Variables หรือ `sessionStorage` ภายใต้ชื่อคีย์ `astro-real-app:rollback-buffer:v1`)
2. **Atomic Write & Rollback Execution**:
   ระบบจะเริ่มทำการลบและอัปเดตคีย์ตามเป้าหมาย หากเกิดข้อผิดพลาดขึ้นในระหว่างเขียนคีย์ใดคีย์หนึ่ง ระบบจะยกเลิกการเขียน และทำการดึงข้อมูลสำรองจาก Rollback Buffer เขียนกลับคืนสภาพเดิมทันทีเพื่อให้ LocalStorage คงสถานะเสถียรดั้งเดิม
3. **Backup-Before-Restore Rule**:
   บนอินเตอร์เฟซ UI ของแท็บเครื่องมือข้อมูล จะมีปุ่มแนะนำให้ผู้ใช้งานกด **"ดาวน์โหลดไฟล์สำรองข้อมูลปัจจุบัน"** เก็บไว้ก่อนเสมอ เพื่อให้มีไฟล์กันเหนียวแบบออฟไลน์ กรณีที่ผู้ใช้ต้องการสลับคืนสภาพข้อมูลดั้งเดิมในอนาคต

## 12. Failure Handling & Overwrite Prevention (การจัดการความผิดพลาด)

- **ความล้มเหลวจากการแปลง JSON (Parsing failure)**: หากโครงสร้างไฟล์ดิบไม่ใช่ JSON ที่มีโครงสร้างตรงตามมาตรฐาน ระบบจะทำการแสดง Error บล็อกการนำเข้า และอธิบายข้อผิดพลาดแก่ผู้ใช้โดยไม่มีผลกระทบต่อเบราว์เซอร์
- **ความผิดพลาดโควต้าเต็ม (QuotaExceededError)**: เมื่อตรวจจับขีดจำกัดหน่วยความจำเกินเกณฑ์ ระบบจะยกเลิกการแก้ไขและเรียกใช้กระบวนการย้อนกลับสถานะเดิม (Rollback) ทันที
- **ความผิดพลาดจากการละเมิดขอบเขตคีย์**: ระบบควบคุมการเขียนข้อมูลจะระบุอาร์เรย์คีย์เป้าหมายอย่างชัดเจน ป้องกันไม่ให้แฮกเกอร์ใช้คีย์แปลกปลอมเข้าแทรกแซงหรือเขียนทับข้อมูลสำคัญในส่วนอื่นของแอปพลิเคชัน

## 13. Manual QA Plan (แผนการทดสอบเชิงปฏิบัติตัวอย่าง)

แผนการตรวจสอบฟังก์ชันในรอบการอิมพลีเมนต์ DEV-046:
1. **ทดสอบการกรองข้อมูลพัง (Malformed File Check)**:
   - ทดลองอัปโหลดไฟล์ที่มีไวยากรณ์ผิดพลาด ไฟล์ขนาดว่างเปล่า หรือไฟล์รูปภาพจำลอง ตรวจเช็คว่าระบบปฏิเสธการอัปโหลดและขึ้นป้ายความผิดพลาดอย่างถูกต้อง
2. **ทดสอบโหมดสแกนแห้ง (Dry Run Validation)**:
   - เลือกไฟล์สำรองข้อมูล JSON ที่ตรงตามสกีมา ตรวจเช็คว่าระบบรายงานรายละเอียดชื่อโปรไฟล์ วันที่ส่งออก และสถิติจำนวนประวัติสะท้อนคิดอย่างชัดเจนบนหน้าจอ โดยไม่พบข้อมูลเปลี่ยนแปลงใน LocalStorage จริง
3. **ทดสอบการทำงานของโหมด Merge-Safe**:
   - บันทึกข้อมูลประวัติสะท้อนคิดลงในเครื่องปัจจุบัน
   - อัปโหลดไฟล์กู้คืนที่มีรายการประวัติสะสมใหม่ร่วมกับรายการเดิม ตรวจสอบว่าระบบผสานข้อมูลเข้าด้วยกันอย่างสมบูรณ์แบบโดยไม่ทำการลบหรือเขียนทับบันทึกปัจจุบันในเครื่อง
4. **ทดสอบการทำงานของโหมด Replace**:
   - เปิดใช้งานการเขียนทับทั้งหมด กดยืนยันผ่าน Dialogue ตรวจสอบว่าประวัติบันทึกสะท้อนคิดและโปรไฟล์วันเกิดถูกอัปเดตตรงตามไฟล์สำรองข้อมูล JSON
