# แผนการบันทึกข้อมูลถาวร (Persistence Plan) — Astro Real App

เอกสารฉบับนี้กำหนดทิศทาง กลไกความปลอดภัย โครงสร้างคีย์จัดเก็บ และพฤติกรรมสำรองในการทำงานร่วมกับพื้นที่จัดเก็บข้อมูลในเครื่อง (LocalStorage) สำหรับระบบ **Astro Real App** เพื่อใช้เป็นคู่มืออ้างอิงในการเริ่มลงมือเขียนโค้ดในขั้นตอนถัดไป (DEV-012) โดยหลีกเลี่ยงผลกระทบต่อระบบโค้ดเดิม

---

## 1. วัตถุประสงค์ (Purpose)
เพื่อออกแบบสัญญาระหว่างระดับข้อมูล (Data Layer) และระดับการแสดงผล (UI Layer) ผ่านอินเทอร์เฟซ `AstroStrategyDataAdapter` โดยระบุแนวทางการโหลดข้อมูล การบันทึกข้อมูลแบบดราฟต์และถาวร รวมถึงการสร้างเกราะป้องกัน (Guardrail) ไม่ให้ข้อมูลทับซ้อนหรือขัดแย้งกับแอปโปรโตไทป์หลัก

---

## 2. ภาพรวมโครงสร้างข้อมูลปัจจุบัน (Current Data Model Overview)
แอปพลิเคชันจะแยกโมเดลข้อมูลที่จำเป็นออกเป็น 4 ส่วนหลัก:
1. **Today Timing Brief** (`AstroTodayData`): ข้อมูลจังหวะเวลา ทิศทางกลยุทธ์ คำแนะนำ ความเสี่ยง และคำถามสะท้อนคิดประจำวัน
2. **Reflection Draft** (`AstroReflectionDraft`): ดราฟต์ของการบันทึกสะท้อนคิดที่ผู้ใช้กำลังพิมพ์ (กันข้อมูลหาย)
3. **Reflection History Logs** (`ReflectionHistoryItem[]`): รายการประวัติที่เซฟเก็บไว้ย้อนหลัง
4. **Strategy Planning Notes** (`AstroPlanningNotes`): แผนกลยุทธ์ส่วนตัว (Focus Next, Slow Down, Next Small Action, Review Later) พร้อมเวลาอัปเดตล่าสุด

---

## 3. การแบ่งหมวดหมู่ข้อมูล (Data Categories)

### A) Persisted User Data (ข้อมูลที่ต้องบันทึกจริง)
ข้อมูลส่วนนี้เกิดจากแอ็กชันของผู้ใช้ และจำเป็นต้องเซฟลงใน LocalStorage:
- **ข้อมูลประวัติสะท้อนคิดย้อนหลัง** (`historyLogs`): เมื่อกดบันทึกเข้าประวัติ
- **ข้อมูลแผนงานเชิงกลยุทธ์ส่วนบุคคล** (`planningNotes`): บันทึกผ่านทางฟอร์ม Strategy Planning Notes
- **ดราฟต์บันทึกสะท้อนคิดชิ้นปัจจุบัน** (`reflectionDraft`): บันทึกฟิลด์ที่กำลังพิมพ์เพื่อป้องกันการรีเฟรชหน้าแล้วข้อมูลหาย

### B) Derived Data (ข้อมูลที่อนุมานได้)
ข้อมูลในกลุ่มนี้จะไม่มีการบันทึกโดยตรง แต่จะถูกคำนวณผ่านการประมวลผล (Derived) จากข้อมูลที่เซฟจริงใน UI:
- **จำนวนประวัติทั้งหมด** (`totalReflectionsCount`): ดึงจาก `historyLogs.length`
- **รายการโหมดการทำงานทั้งหมดที่มีประวัติ** (`uniqueModes`): กรองจาก `reflectionMode` และ `strategyMode` ในออบเจกต์ประวัติย้อนหลัง
- **ระดับพลังงานที่มีประวัติ** (`uniqueEnergies`): กรองจากฟิลด์ `energyLevel` ย้อนหลัง
- **การกรองข้อมูลประวัติ** (`filteredHistoryLogs`): กรองผ่าน search query และ dropdown ต่าง ๆ บนฝั่งไคลเอนต์

### C) Static / Mock / Default Data (ข้อมูลคงที่/ค่าเริ่มต้น)
ข้อมูลคงที่ไม่จำเป็นต้องนำลงฐานข้อมูล/LocalStorage เพราะเป็นฝั่งการนำเสนอเชิงทฤษฎีและเนื้อหาคู่มือ:
- **เนื้อหาคู่มือและกรอบจริยธรรม** (`AstroGuideData`): ข้อมูลในแท็บคู่มือ (Guide & Ethics Panel) ทั้งหมด
- **แผนที่แปลคำศัพท์ภาษาไทย** (`ThaiMap`): การแปลคีย์ภาษาอังกฤษเป็นภาษาไทยในหน้า Today Panel

---

## 4. แผนการกำหนดคีย์ LocalStorage (Proposed LocalStorage Keys)
เพื่อป้องกันการทับซ้อนของข้อมูลกับแอปโปรโตไทป์เดิมและป้องกันระบบพัง จะมีการใช้ Namespace ใหม่ที่เจาะจงเฉพาะตัว real app เท่านั้น:

| ข้อมูลที่บันทึก | คีย์เดิมใน Prototype (ห้ามแตะ) | คีย์ใหม่สำหรับ Real App (เสนอใช้ใน DEV-012) |
|--------------|------------------------------|-----------------------------------------|
| **Reflection History** | `astro-strategy:reflection-history:v1` | `astro-real-app:reflection-history:v1` |
| **Planning Notes** | `astro-strategy:planning-notes:v1` | `astro-real-app:planning-notes:v1` |
| **Reflection Draft** | `astro-strategy:reflection-log:v1` | `astro-real-app:reflection-draft:v1` |

---

## 5. การจัดการเวอร์ชันและการย้ายโครงสร้างข้อมูล (Versioning & Migration Plan)

- **โครงสร้าง Payload**: ข้อมูลทุกชิ้นที่เซฟลง LocalStorage จะถูกหุ้ม (Wrap) ด้วยโครงสร้างออบเจกต์ `AstroPersistedPayload<T>` ดังนี้:
  ```typescript
  interface AstroPersistedPayload<T> {
    version: number;     // เวอร์ชันของโครงสร้างข้อมูล (เริ่มต้นที่ 1)
    updatedAt: string;   // เวลาที่บันทึก (ISO string)
    data: T;             // ข้อมูล payload จริง
  }
  ```
- **แผนการ Migration**: ในขั้นตอนการโหลด หากตรวจพบว่าคีย์จัดเก็บเป็นโมเดลเวอร์ชันเก่า หรือข้อมูลไม่มีฟิลด์ `version` ระบบจะรันตัวปรับประเภทข้อมูล (Migration adapter) เพื่อแปลงข้อมูลให้เข้ากับ Schema ปัจจุบันก่อนที่จะส่งคืนให้ UI (ถ้าไม่สามารถแปลงได้ จะมีพฤติกรรม Fallback)

---

## 6. พฤติกรรมการอ่านข้อมูลขึ้นมาทำงาน (Load Behavior)
1. **ตรวจสอบความมีอยู่ (Existence Check)**: อ่านค่าสตริงจาก LocalStorage
2. **การแปลงข้อมูล (Parsing)**: รัน `JSON.parse` ภายใต้กรอบ `try-catch`
3. **ตรวจสอบโครงสร้าง (Validation)**: เช็กความสมบูรณ์ของฟิลด์ที่จำเป็น
4. **การแปลงเวอร์ชัน (Migration)**: ถ้าเวอร์ชันต่ำกว่าที่ระบบรองรับ ให้ปรับ Schema
5. **การคืนค่าข้อมูล (Hydration)**: ส่งออบเจกต์กลับไปยัง UI เพื่อนำไปแสดงผล

---

## 7. พฤติกรรมการเซฟข้อมูล (Save Behavior)
1. **การแปลงกลับเป็นสตริง (Stringification)**: หุ้มข้อมูลด้วย Payload metadata อัปเดต `updatedAt` และแปลงเป็นสตริงด้วย `JSON.stringify`
2. **การเซฟลงดิสก์**: เรียกใช้ `localStorage.setItem`
3. **การดีเด้ง (Debounce)**: สำหรับการพิมพ์ลงฟอร์มและข้อความแบบออโต้เซฟ (Autosave) จะผ่านกลไก Debounce (ประมาณ 500-1000ms) เพื่อหลีกเลี่ยงการเขียนลง LocalStorage ถี่เกินไป

---

## 8. พฤติกรรมเมื่อเกิดข้อผิดพลาด (Error & Fallback Behavior)
- **JSON Invalid (ข้อมูลเสีย)**: หากข้อมูลถูกแก้ไขจนเซฟเป็นสตริงที่ไม่ถูกต้อง ตัว Parser จะรายงานผ่าน Log และเลือกคืนค่ากลับเป็นชุดข้อมูลเริ่มต้น (`MOCK_DATA`) เพื่อไม่ให้หน้าจอพัง
- **Quota Exceeded (พื้นที่เต็ม)**: ตรวจจับ `QuotaExceededError` ในบล็อกเขียน หากเกิดขึ้น จะแจ้งเตือนผู้ใช้ในคอนโซลและปิดการทำงานของ Autosave ชั่วคราวเพื่อป้องกันเบราว์เซอร์ล็อก
- **ตรวจสอบชนิดข้อมูลล้มเหลว (Type Mismatch)**: ล้างข้อมูลชิ้นนั้นและโหลดค่า Mock กลับมาทำหน้าที่เป็น Baseline ปลอดภัย

---

## 9. สิ่งที่ไม่ควรถูกบันทึกถาวร (What Should Not Be Persisted)
- **ข้อพิจารณาทางจริยธรรมและคำแนะนำทางการแพทย์**
- **ทฤษฎีและเกณฑ์คำนวณทางดาราศาสตร์**
- **คำถามสะท้อนคิดประจำวัน (Reflection Prompts)**: เนื่องจากจะหมุนเวียนเปลี่ยนไปตามจังหวะเวลา/โมดูลคำนวณในอนาคต

---

## 10. แนวป้องกันความปลอดภัย (Guardrails)
1. **ไม่แตะคีย์จัดเก็บของ Prototype**: แยก namespace ของคีย์อย่างเด็ดขาด
2. **ไม่ทำลายระบบหน้าจอทดลอง**: แยกโค้ดออกจากหน้าหลัก `/workspaces/astro-strategy` โดยใช้วงปิดใน `real-app-preview` เท่านั้น
3. **ไม่โหลดข้อมูลย้อนหลังข้ามระบบ**: ห้ามนำ Mock data ไปปนกับ LocalStorage ของส่วนงานจริงหรือในหน้า Prototype
4. **จำกัดสิทธิ์เขียนในขั้นตอนจำลอง**: โค้ดทั้งหมดห้ามเชื่อมต่อกับ API หรือฐานข้อมูลจริง จนกว่าจะผ่านการจำลองระบบ LocalStorage ครบวงจร

---

## 11. แผนงานเสนอสำหรับขั้นถัดไป (Proposed DEV-012 Scope)
ในก้าวถัดไป (**ASTRO-REAL-APP-DEV-012 — Implement Real App LocalStorage Adapter v0.1**) จะมีขอบเขตการทำงานดังนี้:
- เขียนคลาสหรือฟังก์ชัน Adapter ที่ทำหน้าที่ `AstroStrategyDataAdapter` โดยเชื่อมต่อกับ LocalStorage ตามแนวทางที่กำหนดในเอกสารฉบับนี้
- เพิ่ม Client-side context หรือ custom hook เพื่อจัดการสภาวะการทำงานและการอ่าน/เขียนลง LocalStorage ในหน้าจอ Preview เท่านั้น
- สร้างปุ่มจำลองการล้างแคช/ข้อมูลในพื้นที่ เพื่ออำนวยความสะดวกในการตรวจสอบพฤติกรรม Error/Fallback
