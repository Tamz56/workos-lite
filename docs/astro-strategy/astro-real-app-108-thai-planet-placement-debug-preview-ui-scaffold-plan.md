# Thai Planet Placement Debug Preview UI Scaffold Plan (DEV-108)

เอกสารแผนงานโครงสร้างหน้าจอแสดงผลวินิจฉัยตำแหน่งดวงดาวจำลอง (UI Scaffold Plan) สำหรับแผงวินิจฉัยเฉพาะผู้พัฒนา (Debug-only Panel) เพื่อกำหนดขอบเขตคอมโพเนนต์ ตำแหน่งไฟล์ รูปแบบ Layout, กฎการแสดงผลข้อมูล และการควบคุมระดับการมองเห็นอย่างเข้มงวด

---

## 1. Purpose (วัตถุประสงค์)

แผนฉบับ DEV-108 นี้กำหนดรายละเอียดโครงสร้างหน้าจอ (UI Scaffold) สำหรับแผงวินิจฉัยตำแหน่งดาวเคราะห์ไทยรุ่นจำลอง (Stub) เพื่อเตรียมความพร้อมในการพัฒนารหัสคอมโพเนนต์เฉพาะแบบปิด (Debug-only diagnostics) ในเฟสถัดไป โดยเน้นการจัดระดับสิทธ์การแสดงผลและการคัดแยกข้อความให้ปลอดภัยสูงสุด

---

## 2. Scope and Non-goals (ขอบเขตและข้อกำหนด)

* **ขอบเขตแผนการดำเนินงาน (Scope)**:
  * การกำหนดขอบเขตคอมโพเนนต์วินิจฉัย (Component Boundary)
  * การแนะนำเส้นทางจัดเก็บไฟล์ในอนาคต (Proposed Future File Location)
  * โครงสร้างของบล็อกการจัดรูปเลย์เอาต์ย่อย (Layout Blocks) ทั้ง 5 บล็อก
  * กฎเกณฑ์การควบคุมการรับชมข้อมูล (Data Visibility Rules) และพฤติกรรมการคลิกเลือก (Interaction Rules)
  * กฎระเบียบความปลอดภัยด้านการใช้ภาษา (Copy Safety Rules) และความปลอดภัยการออกแบบสี (Visual Safety Recommendations)
* **ขอบเขตที่ยกเว้น (Non-goals)**:
  * **ไม่มีการสร้างหรือแก้รหัส UI จริง**: ห้ามแก้ไขไฟล์ `.tsx` ในโฟลเดอร์ `src/` ในรอบนี้
  * **ไม่มีการดัดแปลงฐานข้อมูลและ LocalStorage**: ไม่มีคำสั่งจัดเก็บค่าตำแหน่งดาวเคราะห์ใดๆ
  * **ไม่มีลอจิกดาราศาสตร์เพิ่ม**: ห้ามคำนวณราศี/องศาจริง หรือเพิ่ม dependencies ภายนอก
  * **ไม่มีระบบตีความความหมาย**: ห้ามแปลสัญญาณจำลองมาเป็นกลยุทธ์ชี้นำชีวิตของผู้ใช้

---

## 3. Proposed Component Boundary (ขอบเขตคอมโพเนนต์ที่นำเสนอ)

* **ชื่อคอมโพเนนต์ที่แนะนำ**: `ThaiPlanetPlacementDebugPanel`
* **ขอบเขตหน้าที่ความรับผิดชอบ (Boundary Rules)**:
  * คอมโพเนนต์นี้มีบทบาทด้าน **การทดสอบ/วินิจฉัยภายในเท่านั้น (Debug-only Component)**
  * **แยกขาดจากแผงหลัก**: ต้องไม่เข้ามารวมอยู่ใน Today, Weekly หรือ Monthly strategy guidance panels
  * **ไม่พัวพันกับชั้นตีความ**: ห้ามอิมพอร์ตไปประมวลผลร่วมกับ Composer หรือระบบ Natal strategy signal
  * **ปลอดสถานะความคงอยู่**: ไม่มีพร็อพส์ผูกเข้ากับการโหลด/บันทึก และไม่ถูกดึงไปแสดงให้ผู้ใช้ทั่วไปเห็นในฐานะข้อมูลตำแหน่งดาวจริง

* **ตำแหน่งไฟล์ที่แนะนำ**: 
  `src/components/workspaces/astro-strategy/real-app/components/diagnostics/ThaiPlanetPlacementDebugPanel.tsx`
* **เหตุผลทางสถาปัตยกรรม**:
  * โฟลเดอร์ย่อย `components/diagnostics/` บ่งชี้จุดประสงค์อย่างเด่นชัดว่าใช้สำหรับงานตรวจวัดความถูกต้องและรายงานสัญญาทางเทคนิค (Contract verification) แยกออกจากโฟลเดอร์คอมโพเนนต์ใช้งานทั่วไปอย่าง `components/` ธรรมดา ช่วยป้องกันไม่ให้นักพัฒนาสับสนและนำไปอิมพอร์ตบนหน้าจออื่นโดยพลการ

## 5. Proposed Layout Blocks (โครงสร้างบล็อกการจัดรูปหน้าจอ)

แผงควบคุมในอนาคตจะจัดแบ่งเป็น 5 ส่วนสำคัญ ดังนี้:

### A. Header block (ส่วนหัวเรื่อง)
* **Title**: `Thai Planet Placement Diagnostics` (ระบบวินิจฉัยดวงดาวไทยจำลอง)
* **Status Badge**: `Stub-only / Not validated` (โครงจำลอง / ยังไม่สอบเทียบ)
* **Warning Copy**: แจ้งเตือนสั้นๆ บ่งบอกสถานะการรันเฉพาะกลุ่มเพื่อตรวจสอบความมั่นคงของสัญญาข้อมูล

### B. Adapter status block (ส่วนสถานะอแดปเตอร์)
* แสดงผลค่าคุณสมบัติเชิงเทคนิคจาก Orchestrator:
  * `adapterStatus` (คาดหวังค่า: `stub-only`)
  * `inputStatus` (คาดหวังค่า: `pending` หรือ `unavailable` ตามข้อมูลเข้า)
  * `generatedAt` (แสดงเป็นข้อมูลอ้างอิง metadata เท่านั้น)

### C. Safety summary block (ส่วนภาพรวมความปลอดภัย)
* รายงานสถานะประเมินภัยจากระบบกักภัย (Safety Harness Summary):
  * จำนวนดวงดาวทั้งหมดที่ประเมิน (Total Planets: 10)
  * ดาวที่มีค่าจำลองค้างรอการตรวจสอบ (Pending Count: 10)
  * ดาวที่เทียบเคียงผ่าน (Comparable Count: 0)
  * ดาวที่ระบุว่าเทียบเคียงไม่ได้ (Not-comparable Count: 10)
  * จำนวนที่ตรวจสอบว่าเสถียร (Validated Count: 0)
  * รายการข้อกังวลที่ตรวจพบ (Issues Count: 0)

### D. Planet placement table (ตารางพิกัดดวงดาว)
ตารางแสดงผลคุณสมบัติเชิงสัญญาข้อมูล โดยแบ่งหัวคอลัมน์ออกเป็น:
* `Planet ID` (แสดงค่ารหัส ๐ ถึง ๙)
* `Sign/Rasi` (แสดงค่าดิบ `pending-reference-validation`)
* `Degree` (แสดงค่าดิบ `pending-reference-validation`)
* `Confidence` (แสดงระดับความเชื่อมั่นเชิงโครงสร้าง เช่น `pending`)
* `Validation Status` (แสดงสถานะ `not-validated`)
* `Notes` (หมายเหตุประกอบ)

### E. Copy safety note (กล่องแจ้งเตือนความปลอดภัยเชิงอักษร)
* แสดงกรอบแจ้งเตือนขอบสีส้ม/เทาเข้มระบุถ้อยคำ:
  * *"สำหรับวินิจฉัยระบบทดลองเท่านั้น ไม่ใช้ประเมินร่วมกับการแปลผลทางโหราศาสตร์ ระบบยังไม่ได้รับการสอบเทียบ และจะไม่มีตำแหน่งดวงดาวจริงแสดงผลในตารางนี้"*

---

## 6. Data Visibility Rules (กฎเกณฑ์การประเมินการแสดงผลข้อมูล)

* **Placeholder Only**: ข้อมูลที่นำมาพิมพ์บนตารางต้องจำกัดอยู่ที่ค่าดิบเชิงสัญญาของ Stub (`pending-reference-validation` หรือ `unavailable`) ห้ามแปรผลเป็นคำอธิบายราศีภาษาไทย (เช่น เมษ, พฤษภ)
* **No Degree Claims**: ห้ามแปลงค่ารอตรวจสอบไปแสดงผลเป็นองศาตัวเลขเปรียบเทียบในเชิงดาราศาสตร์จริง
* **Interpretation Isolation**: ห้ามนำเอาเรนเดอร์ในตารางไปส่งต่อให้ Composer ประมวลผลบทวิเคราะห์ชีวิต

---

## 7. Interaction Rules (พฤติกรรมและการปฏิสัมพันธ์ของผู้ใช้)

* **Collapsible / Accordion Layout**: คอมโพเนนต์นี้ต้องออกแบบให้สามารถพับปิด/เปิดได้ เพื่อลด UI Bloat บน Workspace
* **Read-only interface**: ตารางข้อมูลต้องเป็นโหมดอ่านอย่างเดียว ไม่มีช่องฟิลด์ Input หรือแบบฟอร์มให้กรอกข้อมูล
* **No State Mutators**: ไม่มีปุ่มบันทึก (Save), รีเซ็ต (Reset), หรือการสั่งการส่งออกข้อมูล (Export)
* **Zero Persistence / Analytics**: ไม่มีการเขียนข้อมูลลง LocalStorage และไม่มีการเก็บสถิติผ่านเครื่องมือ Analytics ใดๆ

---

## 8. Copy Safety Rules (กฎความปลอดภัยด้านการใช้ภาษา)

* **ถ้อยคำที่ระบุใช้ได้ (Allowed)**:
  * `"diagnostic only"` / `"สำหรับทดสอบวินิจฉัย"`
  * `"stub-only"` / `"รหัสโครงจำลอง"`
  * `"not validated"` / `"ยังไม่ผ่านการสอบเทียบ"`
  * `"pending reference validation"` / `"รอการวิเคราะห์สัญญาข้อมูล"`
  * `"not used for interpretation"` / `"ไม่ใช้ตีความผลดวงชะตา"`
  * `"not persisted"` / `"ไม่มีการจัดเก็บลงฐานข้อมูล"`
* **ถ้อยคำต้องห้ามเด็ดขาด (Disallowed)**:
  * `"accurate placement"` / `"ตำแหน่งดาวแม่นยำ"`
  * `"real chart"` / `"ดวงชะตาจริง"`
  * `"ดาวสถิตราศี..."` / `"ดาว... ร่วมเรือน..."`
  * `"ผลดวงจริง"` / `"ทำนายผลชีวิต"`
  * `"validated placement"`

---

## 9. Visual Safety Recommendations (คำแนะนำด้านการจัดวางดีไซน์)

* **Muted Technical Design**: จัดแต่งสีสันด้วยโทนสีโมโนโครมหรือสีเทา/ครามทึบ (Neutral status badges) เพื่อลดทอนอารมณ์ความเชื่อส่วนบุคคล
* **No Auspicious Indicators**: ห้ามใช้สีสันสัญลักษ์ เช่น สีเขียว/แดง เพื่อสื่อถึงโชคลาภ เคราะห์กรรม หรือจุดมงคล/อัปมงคล
* **Clear Border separation**: ใส่ขอบกรอบเพื่อจำแนกหน้าต่าง Diagnostics ออกจากแผงประมวลผลดั้งเดิมให้เห็นเด่นชัดสายตา

---

## 10. Integration Guardrails (มาตรการควบคุมความเสถียรเชิงระบบ)

การเขียนคำสั่งเพื่อพัฒนา UI ในอนาคตต้องอยู่ภายใต้เกณฑ์:
1. การเรียกใช้ Orchestrator ดำเนินการใน Memory ระหว่าง Mount เท่านั้น
2. ห้ามแก้ฟอร์มกำเนิด หรือสอดแทรกลิสของ Adapter เข้าสู่ LocalStorage
3. หน้าจอย่อย Debug นี้ต้องไม่แสดงตัวให้บุคคลทั่วไปรับชมได้ (อยู่หลัง flags เสมอ)
4. แสดงผลลัพธ์ของ `adapterStatus` และ `safetySummary` ด้านบนแผงควบคุมเด่นชัด

---

## 11. Risk Review (การประเมินวิเคราะห์ความเสี่ยงเชิงระบบ)

* **ความเสี่ยงการเข้าใจผิดเชิงคุณค่า**: ผู้ใช้งานอาจคาดเดาความหมายจากตารางวิเคราะห์ (แก้โดยใช้ UI แบบกึ่งเทคนิค Muted design)
* **ความเสี่ยงของโค้ดรั่วไหล**: นักพัฒนาอาจนำเอา Adapter ไปติดตั้งผูกรวมกับ Natal Composer ในอนาคตเร็วเกินไป (ป้องกันด้วยการล็อกขอบเขตคอมโพเนนต์ย่อยในระบบ Diagnostics)
* **ผลลัพธ์จาก `generatedAt`**: ผู้ใช้อาจตีความฟิลด์นี้ว่าเป็นเวลาเกิดจริงของผู้พัฒนา (ลดความเสี่ยงโดยการเติมคำว่า `metadata creation time` กำกับท้าย)
